## 面试先回答这几个问题

**Elasticsearch 是面向搜索与分析的分布式系统。** 文本通过分析器变成词项，倒排索引把词项关联到包含它的文档；一次搜索可以分发到多个分片，再由协调节点合并结果。它适合全文检索、日志分析和筛选聚合。涉及余额扣减、跨表事务和强一致业务约束时，通常仍由关系数据库承担事实来源，ES 保存可重建的查询视图。

| 问题                         | 可以直接复述的答案                                                             |
| ---------------------------- | ------------------------------------------------------------------------------ |
| 写入成功为什么搜不到？       | 写入确认与搜索可见是两个时间点，搜索通常需要等 refresh。                       |
| 主分片和副本分片有什么区别？ | 主分片负责对应写入的协调与复制，副本保存数据副本，也可参与搜索。               |
| `match` 和 `term` 怎么选？   | `match` 会按字段分析配置处理查询文本；精确值过滤通常对 `keyword` 使用 `term`。 |
| 深分页为什么慢？             | 每个相关分片需要收集候选结果，跳过越多结果，协调排序成本越高。                 |
| 副本能代替备份吗？           | 不能；错误删除也会被复制，备份需要独立的快照与恢复流程。                       |

## 倒排索引解决的是什么问题

假设有三条商品文档：A 是“轻便登山鞋”，B 是“防水登山鞋”，C 是“轻便背包”。分析后的词项可能包括“轻便”“防水”“登山鞋”“背包”。倒排结构可以把“登山鞋”映射到 A、B，把“轻便”映射到 A、C。搜索“轻便 登山鞋”时，系统先找到候选集合，再根据查询规则计算相关性，而无需逐条扫描全部商品描述。

这里的分词只是教学示意，不能据此假设标准分析器能完成中文词语切分。中文应用要先用 `_analyze` 检查实际词项，再选择满足业务需求的分析器。词典与分析策略改变后，旧文档不会自动按新规则重建，通常需要新索引与重建过程。

`text` 面向分词搜索，`keyword` 面向完整值的匹配、排序、去重和聚合。同一字段可以同时有两种视图。例如商品标题用 `text` 检索，并增加 `raw` 子字段保存 `keyword` 视图。不要为了解决聚合报错就对大量文本字段直接开启 fielddata，应先判断是否真正需要按词项聚合；商品品牌更适合单独存成 `keyword`。[字段类型与多字段说明](https://www.elastic.co/docs/reference/elasticsearch/mapping-reference/text)

## 分片、副本与一次写入的路径

一个索引由若干主分片组成，每个主分片可配置副本。副本提供冗余与读扩展，但也消耗磁盘、网络和写入资源。分片数量并非越多越好：小数据拆成大量分片，会产生额外的元数据、文件句柄、查询调度和内存开销。

一次普通文档写入可以按四步理解：请求到达协调节点；根据路由确定主分片；主分片校验并执行写入；把操作交给当前同步副本集合，完成后返回。副本失败时涉及同步集合调整，不能把它简化为“永远等待配置中的全部副本”。`wait_for_active_shards` 也主要描述执行前的活跃副本要求，不等于整段写入期间永不故障。[官方读写与复制模型](https://www.elastic.co/docs/deploy-manage/distributed-architecture/reading-and-writing-documents)

索引主分片数不能像副本数一样随意动态调整。容量增长时可以通过满足前提条件的 split、reindex 等方式规划迁移。业务使用别名访问索引，可以降低切换时应用代码与物理索引名称的耦合。

## 实战：创建一个可检索、可筛选的商品索引

下面是 Kibana Dev Tools 请求示例。索引名带有学习标识，避免与业务索引混淆；示例只设置字段，不把单节点练习的副本策略当成生产配置。

```http
PUT guide-products-demo
{
  "mappings": {
    "properties": {
      "sku": { "type": "keyword" },
      "title": {
        "type": "text",
        "fields": { "raw": { "type": "keyword" } }
      },
      "brand": { "type": "keyword" },
      "price_cents": { "type": "long" },
      "in_stock": { "type": "boolean" }
    }
  }
}

PUT guide-products-demo/_doc/p1?refresh=wait_for
{
  "sku": "p1",
  "title": "waterproof hiking shoes",
  "brand": "demo",
  "price_cents": 32900,
  "in_stock": true
}

GET guide-products-demo/_search
{
  "query": {
    "bool": {
      "must": [{ "match": { "title": "hiking shoes" } }],
      "filter": [
        { "term": { "in_stock": true } },
        { "range": { "price_cents": { "lte": 40000 } } }
      ]
    }
  }
}
```

这条数据应该满足文本、库存和价格条件。把价格上限改为 30000 后，它应被过滤掉。这个对照可以确认筛选逻辑，而不是只检查 HTTP 状态码。金额使用整数分，避免客户端浮点运算造成业务金额误差；跨币种系统还需要币种字段，不能直接比较不同币种的整数值。

`must` 在此承载相关性查询，`filter` 承载不需要相关性分数的库存和范围条件。过滤上下文有利于表达确定性条件，但不能由此推断每次过滤都必定命中缓存。是否缓存还取决于查询形态和执行策略。

## refresh、持久化与实时查询为什么容易混淆

refresh 让新写入对搜索可见，并不等于备份，也不等于一次完整的磁盘持久化保证。写入耐久性还涉及 translog、同步策略与存储故障模型。按 ID 读取和全文搜索也不能混为一谈：搜索依赖搜索器可见的索引状态。

用户提交商品后立刻进入搜索列表，可在确实需要的写入上使用 `refresh=wait_for`。它通常等待下一次 refresh，减少逐条强制刷新带来的碎片与合并压力。批量导入则应优先使用 bulk、合理批次和并发，避免每条写入都带 `refresh=true`。自动刷新关闭时，`wait_for` 可能长时间等待，调用方仍需超时与错误处理。[refresh 参数与代价](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/refresh-parameter)

## 深分页、同步和故障如何处理

浅分页可以使用 `from + size`。连续浏览大量结果时，选择稳定排序，并把上一页最后一条记录的 sort 值交给 `search_after`；需要保持同一视图时配合 PIT。它适合顺序翻页，并不天然支持直接跳到第十万页。PIT 占用资源，需要合理存活时间并在结束后关闭。[官方分页说明](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/paginate-search-results)

从 MySQL 同步商品到 ES 时，一个可解释的方案是“业务事务写数据库和 outbox，消费者读取事件更新索引”。以业务主键作为文档 ID 便于幂等覆盖，但仍要处理同一商品的事件乱序：旧价格事件迟到，不能覆盖新价格。可以结合业务版本校验、按主键分区顺序消费，以及定期核对修复。同步延迟要作为指标展示，不能将异步搜索视图宣传成强一致结果。

排查慢查询时先看查询耗时分布、返回大小、分片数量、热点、线程池拒绝、磁盘和堆压力，再缩小到某个查询。排查“集群 yellow”时先确认未分配的是副本还是主分片、节点和磁盘分配条件是否满足。单节点无法把同一分片的主副本放到两个不同节点，增加副本数不会凭空产生容灾能力。

## 自测与参考答案

1. **订单已写入 ES，但搜索暂时没找到，是否必须重写一次？** 不必先重写。先核对文档 ID、目标索引、查询条件和 refresh 可见性；无依据地重试可能增加负载，使用随机 ID 时还可能制造重复文档。
2. **品牌筛选为什么不用 `match` 搜商品标题？** 品牌是独立精确属性，应保存为 `keyword` 后过滤，标题包含品牌文字不代表品牌字段就正确。
3. **把副本从一份加到两份，写入一定更快吗？** 不会。复制工作增加，写吞吐可能下降；读性能是否提升还依赖资源余量与负载分布。
4. **怎样确认数据库到 ES 的同步没有悄悄漏数据？** 记录消费延迟、失败与重试，做分区计数或抽样字段核对，并具备按业务数据重建索引的流程；单看消费者进程存活无法证明数据完整。
