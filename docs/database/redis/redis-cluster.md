## 先回答：复制、Sentinel、Cluster 分别解决什么

**复制增加数据副本，Sentinel 为一组主从提供故障发现和自动切换，Cluster 进一步把键分散到多个主节点以扩展容量与吞吐。** 三者都不自动保证业务操作“绝不丢失”或“恰好一次”。选型时先写出数据量、峰值请求、可容忍丢失窗口和故障恢复目标。

| 方案 | 数据分布 | 故障切换 | 适合的约束 |
| --- | --- | --- | --- |
| 主从复制 | 主节点保存完整数据，从节点跟随 | 单独复制不负责完整自动切换 | 备份副本、容忍延迟的只读查询 |
| Sentinel | 一组主从各保存完整数据 | Sentinel 协调提升副本、发现新主 | 单主容量够，需要自动故障恢复 |
| Cluster | 数据按槽分布，每个主分片可有副本 | 分片副本按集群协议参与切换 | 单主容量或吞吐不足、能设计键分区 |

例如，一个缓存总量 8 GB、写入压力不高的服务，不必为了“架构先进”就上分片；如果数据已无法放进单机内存，增加 Sentinel 也不会把数据自动拆开。这里的数字只是选型示例，真正容量要计入对象开销、碎片、复制缓冲和故障期间的余量。

## 主从复制：为什么会有延迟和全量同步

正常情况下，主节点把写操作传播给副本。连接短暂中断后，如果复制历史仍能衔接且 backlog 保留了缺失部分，可继续增量同步；否则需要全量同步。判断依据包括复制 ID 和 offset，而不只是“断线了几秒”。

设复制流峰值约 5 MB/s，希望覆盖 30 秒短暂中断，backlog 至少需要覆盖约 150 MB 的复制流，再根据突发量留余量。**这是估算起点，不是推荐固定配置。** 一次大批量写入、网络恢复速度过慢，都可能让缓冲很快被覆盖。全量同步会消耗网络、生成/加载快照的资源，不能只看客户端 QPS。

业务若在写入后立即从副本读取，可能读到旧值。可采用写后短时间读主、携带版本并在读到旧版本时回源等策略；选择哪一种取决于业务一致性要求。复制不是备份：错误删除也会传播，备份还需要独立保留与恢复演练。[官方复制说明](https://redis.io/docs/latest/operate/oss_and_stack/management/replication/)

## Sentinel 如何判断故障并切换

Sentinel 不接管业务数据请求，它监控主从并提供主节点发现。大致过程是：某个 Sentinel 判断主节点不可达；足够多 Sentinel 形成故障判断；满足选举条件后，由被授权的 Sentinel 组织提升合适副本；其余副本改为跟随新主；客户端重新发现主节点并重连。

**quorum 与多数派不是同一个概念。** quorum 用于形成客观下线判断；真正执行故障转移还要取得多数 Sentinel 的授权。不能把“quorum 设为 1”理解为只剩一台 Sentinel 也总能切换。通常把至少三个 Sentinel 分散到独立故障域，才有能力容忍其中一处故障。

主节点选址、Sentinel 数量、客户端发现配置必须一起验收。如果客户端写死旧主地址，服务端切换成功后应用仍然可能不可用。网络分区中也可能出现旧主仍接受部分客户端写入的窗口；`min-replicas-to-write` 等设置只能限制部分风险，会以写可用性为代价，不能替代严格一致性系统。[官方 Sentinel 说明](https://redis.io/docs/latest/operate/oss_and_stack/management/sentinel/)

## Cluster 的 16384 个槽与客户端重定向

Redis Cluster 将键映射到 16384 个哈希槽，槽再分配给主分片；扩容时移动槽及其数据。它不是“每个节点自动保存所有键”，也不能保证给一个热点键添加节点后就能平均分摊压力。

普通键按键名计算槽。使用 `{...}` hash tag 可以让相关键落在同一槽，例如：

```text
order:{42}:header
order:{42}:items
order:{42}:dedup
```

这便于同槽的多键操作，但如果把所有订单都命名成 `order:{all}:...`，又会把写入集中在一个槽。hash tag 应围绕需要一起操作的业务聚合设计，而不是围绕整个业务域。

槽归属变化时，客户端可能收到 `MOVED` 或 `ASK`：前者指示槽归属需要更新；后者用于迁移阶段的一次临时转向，客户端需按协议处理 `ASKING`，不能直接永久改写槽表。应该使用支持 Cluster 的客户端，并验证拓扑刷新和重试行为。[官方 Cluster 规范](https://redis.io/docs/latest/operate/oss_and_stack/reference/cluster-spec/)

## 一次写入成功后还可能丢吗

可能。默认异步复制下，主节点返回成功后若在副本收到写入前故障，晋升的副本可能没有该写入。`WAIT` 可以让当前连接等待此前写入被指定数量的副本确认，返回值是实际确认数；超时返回不代表此前写入自动回滚，也不能把 Redis 变成强一致系统。

```text
SET order:{42}:status paid
WAIT 1 1000
```

这是同一连接上的说明性例子，不是数据库事务。应用需要检查 `WAIT` 结果，并设计“结果不确定”的处理；不能看到超时就重复执行一次扣费。持久化、副本确认、跨系统事务是三个不同层次。[WAIT 命令说明](https://redis.io/docs/latest/commands/wait/)

**订单金额、账户余额等不可接受丢失的事实通常应由事务数据库记录。** Redis 保存可重建的缓存或协助限流；异步事件通过可靠投递和业务幂等落地。对缓存写失败，可失效并回源，对金融事实写失败则必须追踪事务结果，不能混用补偿语义。

## 设计一个可以说明白的订单缓存

以下是本教程的示例设计：订单事实在数据库；Redis 用 `order:{orderId}:view` 保存摘要并设置过期时间。

1. 修改订单状态时先在数据库事务中提交业务事实，事件可用 outbox 与事实一起持久化。
2. 提交后删除缓存；删除失败由可靠事件重试，事件携带订单版本用于识别旧更新。
3. 读缓存未命中时回数据库，只缓存允许展示的字段；缓存过期加随机抖动，避免批量同时回源。
4. 同一订单突发请求合并回源，并设置并发上限；Redis 整体故障时有控降级，不能把全部请求直接压到数据库。
5. 读写交错仍可能产生短暂旧值。若业务要求严格读到最新状态，关键路径直接查事实库或执行版本校验。

常见错误是“先删缓存、再改数据库”，并发读可能在数据库更新前重新填入旧值；另一个错误是宣称“延迟双删”能无条件解决所有竞态。延迟只能覆盖假定的时序，不能证明慢请求永远不会在删除后回填。

## 扩容与故障排查先看哪些证据

只读观察命令应在你有权限的实例上执行：

```sh
redis-cli -h 127.0.0.1 -p 6379 INFO replication
redis-cli -h 127.0.0.1 -p 6379 INFO memory
# 后两项仅用于已经启用 Cluster 的实例
redis-cli -h 127.0.0.1 -p 6379 CLUSTER INFO
redis-cli -h 127.0.0.1 -p 6379 CLUSTER KEYSLOT 'order:{42}:header'
```

记录复制 offset 差距、链路状态、全量同步次数、内存与碎片、慢命令、被拒绝连接、槽覆盖和重定向错误。观察单个大键与热点分片，不要用平均负载掩盖一个分片已经饱和。迁移前保证新旧节点有余量，迁移中观察延迟和错误率，迁移后核对槽覆盖、副本和客户端拓扑；此处不提供对生产集群直接执行的迁移命令。

## 自测与验收

| 问题 | 合格回答 |
| --- | --- |
| 三个从节点是否意味着数据可以扩大三倍？ | 不会，它们是副本；扩容量需要分片或减少每个实例的数据。 |
| 主节点切换后请求超时，直接重试是否安全？ | 先看操作是否幂等；超时只能说明未拿到结果，不能说明未执行。 |
| 加节点能否解决单个热门商品库存键过热？ | 不会自动拆开单键。要考虑请求合并、业务分片、队列化和热点保护。 |
| Cluster 中为什么脚本报跨槽错误？ | 脚本涉及的键可能分布在不同槽，应按原子性边界设计 hash tag，或重设计跨分片操作。 |
| Sentinel 切换成功就证明高可用验收完成吗？ | 还要测客户端恢复、重试放大、写入结果不确定、业务数据及告警。 |

在隔离环境建立主从或 Cluster 后，先记录一组已确认写入的序号，再模拟节点停止与客户端重连，统计恢复耗时、失败率和丢失窗口；测回源限制是否生效。验收要求来自业务目标，而不是“控制台显示绿色”。这些是待读者执行的练习，不代表本站已完成生产压测。
