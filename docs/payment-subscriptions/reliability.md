可靠性的目标是三件事：购买关系不会被两个账户同时认领；同一履约动作不会重复增加资产；最终权益能够从已验证事实重建。通知实时性、状态查询、历史账单和 CP 履约分别恢复，避免用“接口返回成功”代替端到端结果。

## 乱序不是简单比较时间戳

通知到达顺序不代表业务发生顺序。订阅可以从宽限、hold 或暂停恢复，状态枚举不能按数值只增不减。退款也可能使可访问期限缩短，因此不能无条件取最大到期时间。

处理策略是保留原始事实、核验受影响关系、重算当前投影，并用本地版本或行锁保护并发更新。同订阅分区串行消费只降低并发，不会修复商店源头乱序。

两个渠道查询可能反序完成。可按关系合并刷新任务、分配执行代次并在提交时检查代次和本地版本；旧任务失去提交资格后丢弃或重查。代次只是本地并发护栏，不能证明渠道响应在业务上一定更新；发生矛盾时仍需依据事实语义重新核验。

到期任务携带预期版本与期限，执行前重新比较。旧的到期任务不能关闭已经确认续费的 grant。

## 当前权益与历史账单分别恢复

| 恢复目标 | 依据 | 完成标记 |
|---|---|---|
| 当前访问权限 | 当前渠道状态、有效期和撤销信息 | 权益版本、最后确认时间 |
| 历史交易完整性 | 历史 API／渠道账单／财务报表 | 分页游标、查询范围、对账水位 |
| CP 是否已经发货 | CP 幂等键与执行查询 | 履约状态与结果证据 |
| 业务账户归属 | 既有绑定、可信账户信息及认领策略 | 绑定版本与审计记录 |

Apple 查询历史时按返回关系逐条入账；Google 当前状态接口不等于历史交易账本。商店查询能力存在窗口与保留边界，例如 Google 文档说明 token 在订阅到期 60 天后不再适用于 Developer API 查询，因此已确认事实要及时落库。见 [Google Subscription lifecycle](https://developer.android.com/google/play/billing/lifecycle/subscriptions)。

## 补偿任务的优先级

1. 高优先级：即将触及确认截止时间的新购买、扣款成功但未开通、履约 UNKNOWN。
2. 近期收敛：临界到期关系、宽限或 hold 恢复、渠道查询失败、近期漏通知。
3. 历史回补：缺失账单、财务对账差异、归档恢复。

任务保留 `nextRetryAt`、次数、错误分类、租约与执行代次。限流和暂时故障退避加抖动；归属冲突、签名失败等不能无限当瞬时错误重试。对同一关系合并刷新请求，按渠道配额限并发，避免恢复高峰把渠道 API 打满。

分页完成水位必须随已处理结果可靠保存；失败只重做尚未完成部分。人工修复也走相同的事实处理入口，保留操作原因，不直接随意给会员加一个月。

## 容量分析先区分负载

支付平台日千万级订单约对应 116 笔／秒的全天平均值，但不能当成订阅峰值。首购、续费、重复通知、状态查询、CP 发货和权益读取各有不同放大系数及瓶颈。

| 压力面 | 主要约束 | 观察指标 |
|---|---|---|
| 回调接收 | 验签成本与可靠写入 | P99、接收失败率、最老未处理年龄 |
| 渠道查询 | 渠道配额、延迟和重试放大 | 限流率、查询成功率、待查关系数 |
| 交易入库 | 唯一键竞争、索引与事务耗时 | 锁等待、回滚、每笔写放大 |
| CP 履约 | CP 幂等与处理能力 | UNKNOWN 数、最老未完成年龄 |
| 权益读取 | 本地投影和缓存 | 读取 P99、撤销传播延迟、版本冲突 |

稳定到达率为 λ、处理能力为 μ、积压为 B 时，只有 μ 大于 λ，积压才可能持续下降；理想清空时间约为 `B / (μ - λ)`。还要留出重试、尾延迟和共享资源余量。单实例约 200 QPS 不能脱离硬件、错误率与接口性质简单乘实例数。

## 日本与台湾的写入归属

站点可以同时服务不同用户，但同一订阅关系要有明确唯一主写归属。渠道交易索引、关系认领、订阅写入与履约命令必须遵循一致的 owner 路由。两地数据库分别拥有唯一键，不等于全局唯一。

切换不能只改 DNS。需要隔离旧主写入和旧后台任务，获取新任期，再恢复 Inbox、Outbox 与 UNKNOWN 动作。任期校验应在真正执行副作用的边界生效；先查 Redis epoch 再写库仍存在竞争窗口。

已经发出的 HTTP 请求无法靠提高 epoch 撤回。跨区必须保持同一个稳定 `fulfillmentKey`，由 CP 幂等兜住在途请求；不支持该能力时，切换期间需核验未知结果，不能保证自动重复发货绝不会发生。

## 已扣款已发货但灾备库没有记录

这是异步复制的关键失败场景：日本已提交且 CP 已发货，数据尚未复制到台湾，日本故障。台湾库“查不到”不能证明外部动作没执行。

恢复顺序是确认并隔离旧主，核验渠道购买事实，使用同一履约键查询 CP，分别补齐交易记录和履约结果。CP 已成功时只补本地记录；结果未知时保持 UNKNOWN，不能再次换键发奖励。商店只证明购买事实，不能证明 CP 的资产变化。

同步跨区提交可以缩小关键记录丢失窗口，但会增加延迟并影响网络分区时的写可用性；它仍不能替代外部 CP 的查询和幂等。RPO 应明确保护哪类提交记录，RTO 应明确从什么业务不可用时点算到哪个恢复点。

## 监控与验证清单

| 场景 | 断言 |
|---|---|
| 同一交易从客户端、回调与补偿各进入一次 | 只有一笔交易账单，未完成动作继续处理 |
| 续费后旧到期事件到达 | 新有效权益不被旧事件覆盖 |
| 退款后旧购买通知重放 | 已撤销来源不会重新开通 |
| 两个业务账号并发认领 | 只有可信归属可以成功 |
| CP 已执行但响应超时 | UNKNOWN 最终收敛且增量资产只变化一次 |
| 新主缺少旧主提交记录 | 先恢复事实与 CP 结果，再决定后续动作 |
| 渠道限流或 CP 故障 | 接收可持续、积压可观测、已有权益查询按策略可用 |

核心业务指标包括扣款但无权益、权益落地延迟、重复发货、退款后访问未撤销、确认期限风险与 UNKNOWN 数。技术指标还需看 Inbox／Outbox／履约各阶段最老年龄；MQ lag 为零不代表用户已经拿到权益。
