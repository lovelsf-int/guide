> 从数据模型、失败处理和验证方法复习系统设计题。示例规模是训练假设，设计方案不代表已完成生产压测。

## 怎样把一道系统设计题讲完整

先确认用户是谁、核心操作是什么、预计峰值、允许多长延迟，以及哪些结果绝不能错。画出最短请求链路，再解释数据库的约束、异步事件、缓存和故障恢复。避免一开始就把所有中间件画进架构图。

例如假设每日 1000 万次读取，平均约为 `10,000,000 / 86,400 ≈ 116 QPS`；若假设峰均比 20，则按约 2320 QPS 评估读链路。两者都是需求假设，需要流量证据修正。存储量还要计算索引、副本、日志和保留期限。**系统正确性靠约束和状态机保证，容量靠测量决定。**

本文每题的“验证”都是应执行的验收用例，不是已完成的测试报告。

## 1. 如何设计短链系统

**核心答案：** 用不可重复的短码映射长 URL，数据库保存事实，缓存承担热点跳转。表中至少有 `code` 唯一键、`target_url`、创建者、过期时间和状态。可以用全局唯一 ID 编码成 Base62；随机短码则依靠唯一约束发现碰撞并重试。不同用户对同一 URL 的有效期和统计需求可能不同，不能默认全站按 URL 去重。

创建接口验证协议和长度，只接受约定的 HTTP/HTTPS 地址；如果服务会主动抓取目标，还要防 SSRF。跳转先查缓存，未命中查数据库，过期或禁用返回明确结果。需保留撤销能力时使用可控缓存期限的临时跳转，避免永久重定向被浏览器长期保存。统计事件异步发送，统计故障不阻断跳转。

**失败与权衡：** 不存在的短码可以短时间缓存空值并对扫描行为限流；更新目标后使旧缓存失效，容忍窗口必须与撤销要求一致。自增 ID 暴露数量趋势，不适合必须难以枚举的私密链接；短码也不能代替授权。

**验证：** 并发创建时强制制造短码碰撞；禁用后检查各层缓存；统计服务不可用时跳转仍成功；不存在短码流量升高时数据库负载保持受控。

## 2. 如何设计秒杀系统

把页面展示、资格判断和库存成交分开。静态页走 CDN，入口按活动、账号、设备维度限流；每人限购依靠 `(activity_id, user_id)` 唯一约束。Redis 预扣可以挡住洪峰，但最终订单和库存必须有可恢复的事实记录。

一个便于说明正确性的基础版本是在同一数据库事务中写幂等记录、条件扣库存并创建订单。只在条件更新影响一行时继续，任何一步失败都回滚：

```sql
UPDATE activity_stock
SET available = available - 1
WHERE activity_id = ? AND available > 0;
```

如果升级为 Redis 预占加异步建单，预占记录要有唯一 ID、状态和到期时间，订单消费者按预占 ID 去重；超时释放必须确认该预占没有成功成交。Redis 故障后的库存重建以已落库订单与预占日志为依据，不能简单把库存重置为活动初值。

**失败与权衡：** 返回“已受理”不等于购买成功。把待处理结果提供为查询接口，避免客户端因超时疯狂重复下单。异步化提高缓冲能力，也引入排队时延和补偿成本。

**验证：** 用 100 件库存并发提交 1000 个不同用户请求，成交不得超过 100；同一用户重试只产生一单；在预占后、建单后和确认响应前分别中断流程，检查库存守恒。

## 3. 如何设计动态线程池

将业务线程池注册为 `pool_id -> ThreadPoolExecutor`，配置包含版本、核心线程数、最大线程数、空闲回收时间、拒绝策略及适用实例。更新前验证 `0 <= core <= max`、`max > 0`、`keepAliveTime >= 0`，按版本防止旧通知覆盖新配置，先灰度一小组实例，再观察队列等待时间、任务耗时、拒绝数和下游连接池利用率。

增大核心线程数到超过旧最大值时，先提高最大值；减小最大值到小于旧核心数时，先降低核心值。修改参数不会把正在运行的任务强制停止。常用有界队列没有通用的在线修改容量接口，不能声称调用一次 setter 就能改变既有队列容量；可以选择支持调整的专用队列，或在排空旧池后切换到新池。API 行为以 [ThreadPoolExecutor 文档](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/concurrent/ThreadPoolExecutor.html)为准。

**失败与权衡：** 配置中心不可用时保持最后一次有效配置；调整失败应记录已应用字段并恢复整份旧配置。线程数增大可能压垮数据库，不能只按 CPU 利用率自动扩容。停机先摘流量，再停止接收、等待有界时间，最后记录未完成任务以便恢复。

**验证：** 乱序投递两个配置版本；配置 `core > max`；队列满时调整参数；慢任务运行中执行回滚。检查任务没有静默丢失，拒绝策略符合业务。详见[线程池最佳实践](../java/concurrent/java-thread-pool-best-practices.md)。

## 4. 如何设计站内消息和未读数

消息表保存内容，收件箱表保存 `(user_id, message_id)`、送达状态和已读状态。小规模逐用户写入即可；全站公告可以保存一条公告及用户阅读游标，避免每次广播都写亿级收件箱。事务提交消息与 Outbox 事件后，再异步推送 WebSocket。

WebSocket 只是实时通知通道。客户端重连后按游标拉取持久消息，服务端在落库后确认发送成功。消息 ID 去重；“已读”用条件更新，仅在 `unread -> read` 首次成功时减少计数，重复点击不能重复扣减。未读缓存可由收件箱重新计算，不能让缓存成为唯一事实来源。

**失败与权衡：** 一个账号多设备可能有不同送达游标，但产品通常需要共享已读状态。广播消息与个人消息需分别计数后汇总。删除和撤回要有墓碑或版本，防止离线设备把旧消息恢复出来。

**验证：** 落库后推送前断线，再重连补拉；同一消息重复投递三次；两台设备同时标记已读；缓存清空后重建，最终未读数应与事实表一致。

## 5. 如何设计微博 Feed 流

采用写扩散、读扩散或混合模式。普通作者发帖后异步写入粉丝的收件箱，读时间线较便宜；大 V 的粉丝过多，则保留作者发件箱，读时合并。关注关系、帖子事实和时间线索引分离，避免把一份正文复制到每个粉丝名下。

时间线用 `(created_at, post_id)` 做稳定游标，不能只用时间戳；拉取时按帖子 ID 去重，再做权限、拉黑、删除校验。推荐流可先得到候选、过滤、排序，再保存一段会话候选快照，减少翻页时因分数变化出现重复或跳项。

**失败与权衡：** 写扩散消息丢失可从作者发件箱按游标补偿。取消关注和隐私变更不能只删除缓存，读路径也要校验当前可见性。热点作者扇出任务分批执行并限速；不在线用户可以延迟构建收件箱。

**验证：** 大 V 发帖时测扇出延迟与积压；分页过程中插入新帖；关注后取消再关注；删除帖子后检查旧收件箱。验收指标分别包括首屏延迟、重复率和隐私生效延迟。

## 6. 如何设计排行榜

先约定分数是累计值、时间窗内增量还是可撤销值，以及同分如何排序。单榜规模适中可用 Redis Sorted Set，成员为用户 ID；如果事件至少投递一次，先按事件 ID 去重，再增加分数，或由事实库输出带版本的绝对分数。

热门榜单取前 K，用户查名次走 rank；榜单到结算时生成带版本的快照，分页固定在同一版本，避免实时更新导致上一页和下一页重叠。业务要求“同分按达到时间排序”时应单独设计排序键或合并排序，不要把很大的整数分数和时间随意塞进浮点 score 造成精度丢失。

**失败与权衡：** Redis 榜单只是投影，持久事件或分数事实可重建。跨分片做精确全局 Top K 时，各分片先给出局部候选，再归并；用户跨分片的同一指标必须先完成正确聚合。

**验证：** 重放同一加分事件；同分用户跨页；榜单冻结时仍有迟到事件；清空缓存后重建。Redis 有序集合的语义见[官方数据类型文档](https://redis.io/docs/latest/develop/data-types/compare-data-types/)。

## 7. 点赞、优惠券、红包分别怎么设计

**点赞：** `(user_id, target_id)` 唯一，接口表达“设为已赞/未赞”，比“切换状态”更适合重试。事实变化后发布带版本事件更新计数；旧事件不得覆盖新状态。验证连续点赞、取消、乱序重放后，关系和计数仍一致。热点计数可分桶，但页面允许的统计延迟需明确。

**优惠券：** 券模板管总额度，用户券管归属和状态，订单使用券时用条件更新 `AVAILABLE -> RESERVED` 并绑定订单 ID。支付成功变为已用，订单关闭解除占用；占用、核销和退券各有唯一业务键。验证两个订单同时用同一张券时只能成功一个，以及“退款是否退券”按产品规则执行。

**红包：** 金额用整数分。预先生成金额分配结果时保证每份满足最小金额、总和严格等于总金额；领取以 `(packet_id, user_id)` 去重，再原子占用一份。余额及资金流水由账本记录，过期返还剩余资金需要唯一返还单。验证最后一份领取与过期返还并发，不能出现既领走又退回。

这三题共同点是幂等状态迁移，不是简单地对 Redis 数字加一减一。详见[接口幂等](../high-availability/idempotency.md)。

## 8. 订单超时自动取消如何实现

订单创建时保存服务端 `expire_at` 并发送到期检查事件。消费者到期后重新查订单，用条件更新将 `PENDING` 改为 `CLOSED`；只有状态迁移成功者才释放库存、优惠券等资源。支付回调也只能从允许的旧状态转入已支付，双方竞争同一事实记录。

```sql
UPDATE orders
SET status = 'CLOSED', version = version + 1
WHERE id = ? AND status = 'PENDING' AND expire_at <= CURRENT_TIMESTAMP;
```

事件只是提醒检查，数据库状态才决定是否关闭。定时扫描补偿 `PENDING AND expire_at <= now` 的订单，为该查询建立合适索引。支付渠道若在本地关闭后确认收款，应进入退款或人工对账流程，不能悄悄把已释放库存的订单恢复成交。

**验证：** 到期事件提前、延后、重复、完全丢失；支付回调与关闭在同一毫秒竞争；释放库存失败后重试。最终状态必须可解释，资源释放最多发生一次。

## 9. 如何基于 Redis 实现可靠延时任务

ZSet 的 score 存到期时间，轮询器领取 `score <= now` 的任务；领取时必须原子地从待执行区移到处理中，记录租约、尝试次数和任务 ID。业务处理成功后确认；进程崩溃后由恢复器重投租约到期任务，消费者仍需幂等。单纯 `ZPOPMIN` 后执行，进程崩溃会丢失已弹出的任务。

Redis Cluster 中需要原子操作的键要位于同一槽，或者用支持相应语义的队列实现。对不能丢失的订单任务，数据库任务表保存事实，Redis 负责加速到期索引，并用扫描修复。过期键通知受订阅者在线状态和删除时机影响，不宜作为唯一可靠调度依据。

**失败与权衡：** 轮询间隔决定一部分时效，长任务需要续租，重试使用退避和最大次数，超过阈值进入待处理队列。消费者确认也不能等同于外部副作用恰好一次。Redis Streams 消费组的待确认机制及持久化边界见[官方文档](https://redis.io/docs/latest/develop/data-types/streams/)。

**验证：** 领取后杀掉进程；业务提交后确认前崩溃；Redis 重启和时钟跳变；毒消息持续失败。扩展阅读：[Redis 延时任务](../database/redis/redis-delayed-task.md)。

## 10. 大文件上传、断点续传和秒传

业务服务先鉴权并创建上传会话，返回限定对象和分片的短期上传授权；浏览器直接上传到对象存储，服务端不转发全部字节。会话保存用户、对象键、预计大小、分片规格、已上传分片和状态；同一分片重传应可覆盖或去重。

完成请求由服务端校验实际分片清单、顺序、大小和校验和，再合并并做内容检查，最后将状态从 `UPLOADING` 改为 `READY`。上传成功而业务落库失败时，可用会话 ID 查对象状态继续完成。未完成会话定期清理，防止残留分片持续占空间。

“秒传”只省掉已有内容的重复上传。客户端给出哈希不能证明拥有文件，必须校验访问权，必要时做内容持有证明，不能让攻击者猜一个哈希就下载别人的私密文件。分片上传的 ETag 不能一概视为整文件 MD5；采用存储服务明确支持的校验和方式。[S3 分片上传文档](https://docs.aws.amazon.com/AmazonS3/latest/userguide/mpuoverview.html)

**验证：** 网络中断后仅补缺失分片；乱序/重复分片；声明 10 MB 实际上传 1 GB；合并成功后响应丢失；跨用户猜哈希。确保未完成或未检查的对象不能被公开读取。

## 11. IP 归属地功能如何实现

先从可信反向代理配置中提取客户端 IP，只接受可信代理追加的转发信息，不能无条件信任用户自填的 `X-Forwarded-For`。规范化 IPv4/IPv6，区分私网、回环和无法识别地址，输出“未知”而非编造位置。

高频查询适合离线 IP 库，减少网络延迟和请求泄露；在线服务便于更新但增加超时与成本。离线库按版本下载、校验、预加载后原子切换，保留旧版本回滚。缓存可以按 IP 与库版本联合索引，避免库更新后永久保留旧结果。

**边界：** IP 归属地是网络位置估计，移动网络、VPN 和代理会改变准确性；不能据此断定具体个人或住址。MaxMind 也明确说明其数据无法精确定位个人、家庭或街道地址。[精度说明](https://support.maxmind.com/knowledge-base/articles/maxmind-geolocation-accuracy)

**验证：** IPv6、私网、未知段、代理链伪造和库切换；在线接口超时时页面降级显示未知，登录主流程不应因此阻塞。

## 12. 如何统计 PV、UV、VV 和独立 IP

PV 是页面浏览事件数；UV 是按约定身份键去重的访客数；VV 通常指会话次数，需要给出会话间隔规则；独立 IP 数只统计地址，不能代替人数。先约定时区、一天边界、机器人过滤和登录前后身份合并规则，否则换数据结构也无法保证口径一致。

对运营趋势可按天、租户建 HyperLogLog，`PFADD` 写访客 ID，`PFCOUNT` 读估计值；跨天 UV 用集合合并语义计算，不能把每日 UV 相加。Redis 的 HLL 是近似基数估计，官方给出的标准误差约为 0.81%，不是每次都保证误差小于该值，也不能查询某个用户是否来过。[官方说明](https://redis.io/docs/latest/develop/data-types/probabilistic/hyperloglogs/)

计费、权益核销等需要精确人数时，使用事实事件及精确去重存储。迟到事件按事件时间归属窗口，报表说明何时完成结算。

**验证：** 同用户多次访问、匿名转登录、跨午夜、消息重复和迟到；用已知基数的数据集比较统计口径及估计误差。

## 13. 限流、幂等和缓存穿透怎么组合

先在网关限制入口速率，再对昂贵业务按账号、租户和资源限制并发。令牌桶允许一定突发，滑动窗口适合近一段时间配额；分布式限流需要原子更新。多个实例各限 100 次并不等于全局限 100 次，必须明确分配和超额语义。

幂等键绑定调用方、操作和请求摘要：同键同请求返回原结果，同键不同请求拒绝。把业务提交和幂等结果放进同一事务，或建立可恢复状态机。缓存穿透先校验参数，对确实不存在的对象短暂缓存空值；Bloom Filter 可以做入口过滤，但新增数据必须及时加入，不能把尚未同步的数据拒之门外。

**失败与权衡：** 限流存储故障时，支付类写操作可以拒绝并要求重试，普通读可降为本地保守限流；策略必须按业务选择。缓存故障时控制回源并发，避免全部请求直冲数据库。

**验证：** 同幂等键并发请求、参数变更、缓存失效洪峰、过滤器重建期间新增数据。参考[限流](../high-availability/limit-request.md)、[幂等](../high-availability/idempotency.md)、[Redis 常见问题](../database/redis/redis-questions-02.md)。

## 14. 敏感数据脱敏和敏感词过滤有什么区别

手机号、证件号的脱敏是减少数据暴露，敏感词过滤是内容识别，不能混为同一种正则替换。结构化数据在输出 DTO、日志和导出层按字段执行掩码或不可逆化，规则应包含角色与用途；数据库加密解决另一层问题，不能代替输出权限控制。

敏感词处理可用规范化后的文本和多模式匹配索引，但规范化可能改变语义，要保留可审计的规则版本和判定原因。规则热更新先构建完整新索引再原子替换，避免一半新规则一半旧规则。对复杂正则设置长度及耗时限制，防止灾难性回溯。

**失败与权衡：** “张三”被掩码不代表其他字段无法重新识别。可搜索的明文索引、异常堆栈、埋点也属于暴露路径。审核系统要有人工纠错通道，不能把词表命中直接等价成用户违法。

**验证：** 日志、下载、异常页和异步消息中的敏感字段；Unicode 变体及超长输入；规则更新并发读取。详见[数据脱敏](./security/data-desensitization.md)。

## 15. 如何安全传输和存储密码

密码通过正确验证证书的 HTTPS 传输，前端先做一次普通哈希不能替代 TLS，因为那个哈希值本身可能成为可重放凭据。服务端用专门的慢速密码哈希算法、独立随机盐及版本化参数保存验证值，不存明文或可逆密文作为常规登录凭据。

新系统优先评估 Argon2id；已有 bcrypt 系统需要理解 72 字节限制，不能静默截断长密码。成本参数要在目标环境基准测试，兼顾抗离线猜测成本和登录容量。可选的 pepper 应与数据库分开存储并设计轮换恢复方案。具体算法建议见 [OWASP Password Storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)。

**失败与权衡：** 哈希只能提高数据库泄露后的破解成本，不能阻止在线撞库；还需要登录限速、异常检测和高风险操作再次验证。重置密码用短期、单次令牌，重置后撤销适当范围的旧会话，不提供“找回原密码”。

**验证：** 相同密码生成不同盐和验证值；参数升级后旧密码仍能验证并逐步迁移；日志无明文；超长和非 ASCII 密码不会被意外截断。参考[为什么只能重置密码](./security/why-password-reset-instead-of-retrieval.md)。

## 16. 第三方授权登录怎样实现

登录通常在 OAuth 2.0 授权码流程上使用 OpenID Connect 的身份层。客户端发起时生成随机 `state`、PKCE verifier/challenge，按需要生成并保存 `nonce`，将它们绑定到短期登录会话。回调验证状态，服务端用授权码与 verifier 换令牌，校验 ID Token 的签名、issuer、audience、时效和 nonce，再用 `(issuer, subject)` 找本地账户。[OIDC Core](https://openid.net/specs/openid-connect-core-1_0.html)

OAuth 的授权能力本身不自动证明用户身份。没有 OIDC 的平台要按其官方身份接口核验，不能从前端传来的昵称或邮箱直接建立信任。账号绑定需要现有账号重新验证，不能只因两个提供商给出相同邮箱就无条件合并。

**失败与权衡：** 回调地址应严格注册与匹配，禁止任意跳转；授权码单次消费，回调重复时安全返回已有处理结果。访问令牌尽量留在服务端，日志不要记录令牌或授权码。安全建议参照 [RFC 9700](https://www.rfc-editor.org/rfc/rfc9700.html)。

**验证：** state 不匹配、错误 audience、过期令牌、重复回调、账号绑定劫持和多提供商混淆；提供商超时不能创建半完成账号。

## 17. 验证码登录如何设计

验证码由安全随机源生成，保存挑战 ID、用途、目标、过期时间、尝试次数和消费状态。对短数字码使用服务端密钥参与的验证值，避免数据库泄露后轻易枚举；发送接口按账号、设备、IP、渠道预算多维限速，不在日志中记录验证码。

校验时把“匹配、未过期、未消费、扣尝试次数或标记消费”放进原子操作，成功后建立会话。登录码、改密码和换绑码必须隔离用途；重发策略明确是使旧码失效还是沿用当前挑战，不允许多个有效码无限累积。目标账号是否存在采用尽量一致的对外提示。

**失败与权衡：** 短信可能重复、延迟或被运营商重排；发送请求幂等，渠道响应不明确时先查询状态或限额重试。短信验证码并非高保证身份凭证，敏感操作可要求更强验证。

**验证：** 同一个验证码被两条请求同时提交，只能消费一次；错误尝试耗尽后即使输入正确也不能继续；换手机号后旧挑战无效；发送风暴不突破渠道预算。

## 18. 密码多次输错后如何限制登录

分别统计账号、来源 IP、设备和网段风险：只限 IP 会误伤共享出口，只锁账号会让攻击者批量锁死其他人。可采用短时间窗口计数加逐步退避，超过阈值追加验证；对高风险来源加严，对已验证设备保留受控恢复路径。

计数和过期必须原子设置，避免 `INCR` 后进程崩溃导致计数永不过期。验证密码前先检查是否受限，失败后更新风险，成功后按策略清除相应计数。对外错误信息尽量不泄露账号存在性，日志记录原因但不记录密码。OWASP 对节流、锁定与恢复的取舍有专门说明：[Authentication Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html)。

**验证：** 多实例并发错误尝试、IP 轮换、同 NAT 多用户、账号锁定攻击，以及计数存储故障。验收既看撞库阻断，也看正常用户恢复路径。

## 19. 40 亿个 QQ 号，1 GB 内存如何精确去重

先问号码的**值域**，不能根据“40 亿条记录”就推出需要 40 亿位。如果所有号码是无符号 32 位整数，则整个值域有 `2^32` 个值，一位表示是否出现，需要 `2^32 / 8 = 512 MiB`，可在 1 GiB 内存约束下留出输入输出缓冲。扫描记录设置位图，再按置位位置输出唯一号码。

若号码值域更大或者是字符串，完整位图不再合适。按稳定哈希分到多个磁盘分区，使相同号码总在同一分区；逐分区装入内存去重，再输出。单分区仍过大就继续分区或外部排序。精确方案必须比较原始键，不能把哈希碰撞当成同一号码。

**失败与权衡：** Bloom Filter 有假阳性，直接丢弃“可能存在”的记录会丢掉真实唯一值，不能单独用于精确去重。分区数根据每条数据的实际存储开销及内存预算计算，并考虑数据倾斜。

**验证：** 包含最大/最小值、全重复、全不同、热点号码和哈希碰撞的样本；分区重试不会重复输出；结果与小样本精确集合交叉核对。详见[布隆过滤器](../cs-basics/data-structure/bloom-filter.md)。

## 20. 日活上亿，如何避免重复推荐视频

先约定“重复”是本次会话、最近 30 天还是永久看过，以及是否允许重复推荐但不自动播放。写入“已曝光”和“已观看”是两个口径，不能只在播放完成时记录，否则快速滑动会反复出现。

单用户近期开启精确集合或按天分桶的压缩集合；长历史可用 Bloom Filter 做候选快速排除，接受假阳性意味着少推荐一些未看过视频。必须完全准确时，需要精确历史索引兜底。召回后先去重，再排序，返回批次分配 request ID，曝光回传按事件去重；在回传延迟期间，服务端维护会话内已分配候选集合。

**失败与权衡：** 多设备共享历史存在同步窗口；过滤器版本和过期窗口应一致，普通 Bloom Filter 不支持安全删除单个元素。用户隐私删除需覆盖事实历史和派生结构，必要时重建。

**验证：** 同设备连发两页、跨设备同时请求、曝光回传丢失、过滤器达到设计容量以及历史删除。指标同时观察重复率、候选损失率和延迟。

## 21. 海量数据 Top K 怎么做

若问题是“最大 K 个数”，维护大小为 K 的小顶堆，读到更大值替换堆顶，时间 `O(N log K)`、额外空间 `O(K)`。数据能放进内存且允许重排时可用 Quickselect，平均线性时间，但最坏情况和实现细节要说明。

若是“出现次数最多的 K 个词”，必须先按词汇总次数，再选 Top K。多机随机分片后直接取各片局部频次 Top K 并不能保证精确结果：一个词可能在每片都排第二，合计后却全局第一。正确做法是按键分区并聚合，同一个词的所有次数归到同一逻辑分区，再对各分区聚合结果取候选并归并。

**失败与权衡：** 单个热点键可以先做分片局部计数，再二次汇总，避免一台 reducer 被打满。流式 Top K 必须给出窗口、迟到数据与撤回规则；近似算法要明确误差和可接受用途。

**验证：** 构造“各分片第二但全局第一”的反例、同分名次、极端热点和迟到事件；精确结果对照离线全排序基线。

## 22. 多位骑手抢一个订单如何保证只成功一人

抢单的唯一归属由数据库条件更新决定：

```sql
UPDATE delivery_order
SET rider_id = ?, status = 'ASSIGNED', version = version + 1
WHERE id = ? AND status = 'WAITING' AND rider_id IS NULL;
```

影响行数为 1 才是成功。同一骑手请求重试时查询既有归属，返回相同结果；不同骑手失败返回已被领取。还要在同一事务内校验骑手运力或占用额度，避免某骑手同时抢到超过上限的订单。通知、搜索索引等副作用由提交后的可靠事件驱动。

**失败与权衡：** Redis 锁可以减少竞争，但不能替代数据库约束。若业务允许超时释放再派单，订单需要分配版本，旧骑手携带旧版本的完成请求必须拒绝，避免“僵尸执行者”继续操作。

**验证：** 100 个骑手同时抢同一订单；获胜响应丢失后重试；取消与抢单并发；重派后旧客户端继续操作。详见[乐观锁与悲观锁](../java/concurrent/optimistic-lock-and-pessimistic-lock.md)。

## 23. 提现失败或退单怎样处理

提现先把余额从可用转为冻结，并创建唯一提现单；向渠道发送固定商户单号，记录提交状态。渠道成功后冻结资金转为已出款，确认失败后才解冻。网络超时属于结果未知，不能立即退回余额后用新单号再次付款。

状态机可设为 `CREATED -> PROCESSING -> SUCCEEDED / FAILED`，未知结果保持处理中并查单。回调验签，核对商户、金额、币种和订单号；以渠道事件 ID 或业务状态去重。账本写冲正流水表达退款/退单，保留原始成功事实，不直接删除流水或覆盖历史余额。

**失败与权衡：** 同一个业务操作的状态、资金流水和 Outbox 事件应在本地事务中提交。外部渠道不能参加同一事务，因此需要查单、重试和按账单对账。出现“本地失败、渠道成功”时先冻结处理权限并核对，不盲目再次出款。

**验证：** 回调重复、乱序和伪造；渠道成功但响应丢失；查单与回调竞争；退单重复送达。逐币种检查资金守恒，资金差异进入可追踪的人工处理队列。

## 24. 抽奖系统如何保证库存、资格和概率正确

先明确概率含义：固定奖项权重、奖池耗尽后概率变化、每人次数、是否保底等都是产品规则，不能写完随机数再倒推。抽奖请求带幂等键，在事务中占用抽奖资格并保存一次结果；重复请求必须返回同一结果，不能再摇一次。

随机选择使用适合业务的随机源，按版本化奖池配置生成结果，再原子扣减对应库存；扣减失败时按预先定义的规则重选或返回未中奖，不能临时改变承诺。发奖异步执行，发奖单唯一，物流或兑换服务超时时查询原单状态。结果记录奖池版本和规则版本，便于审计。

**失败与权衡：** 先随机后扣库存和先分配奖池都有不同的概率分布，尤其在奖品售罄边界。现金类奖励还需要严谨账本与规则审查，普通活动代码不能直接承担资金结算。

**验证：** 同一请求重试、资格重复消费、最后一个奖品并发、发奖成功后确认丢失；用大量模拟检查分布是否符合约定，并单独验证库存和资格守恒。

## 25. 即时聊天如何保证可恢复和会话内顺序

每个会话为消息分配单调序号，客户端用 `client_message_id` 幂等发送。服务端将消息持久化后再确认接收，在线通过 WebSocket 投递；用户重连时提交最后收到序号补拉，不能把 TCP 连接建立当成消息已送达。

服务端已收、设备已收和用户已读是三种状态。客户端按消息 ID 去重，以会话序号排序，遇到缺口发起补拉。多设备使用各自同步游标，共享已读状态按产品规则合并；跨会话通常不承诺全局顺序。

**失败与权衡：** 把序号分配与消息落库分成两步可能留下空洞，需事务、会话分区单写者或显式空洞处理。大群广播使用分层扇出和按需补拉，不能为每次消息创建无界并发任务。

**验证：** 发送后确认前断线、同一消息多次重发、离线数日后同步、会话迁移和撤回消息。检查已确认消息可恢复、重复消息不重复展示、乱序最终收敛。

## 26. 支付回调与主动查询怎样保持一致

回调入口验签并核对商户、渠道单号、币种、金额和本地订单绑定，不能只凭一个“支付成功”字符串改状态。将渠道事件唯一键、订单状态更新、支付流水和后续发货事件写入同一事务，再返回渠道确认。

主动查询和回调共用一套状态迁移函数。重复成功只返回已有结果，旧的处理中状态不能覆盖已成功；订单已关闭却确认付款时进入退款或人工处理分支。订单成功与发货成功分开记，发货消费者按订单或发货单唯一键处理，避免回调重试导致重复发货。

**失败与权衡：** 渠道回调也可能丢失，定时查单与账单对账负责补偿。若本地数据库不可用，不应先返回已受理成功再丢弃事件；保留渠道重试能力或先持久化到可靠入口队列。

**验证：** 重复回调、错误金额、验签失败、查单和回调并发、数据库提交后响应丢失。核心指标是账实差异、未知状态滞留时长和重复副作用次数。

## 复习时怎么自查

任选一题，先用两分钟说出最短链路，再回答四个追问：事实保存在哪里；两条相反请求同时到达谁获胜；成功提交后响应丢失如何恢复；怎样用测试证明约束没有被破坏。能说清这四项，再讨论分片、缓存和扩容，答案会更扎实。
