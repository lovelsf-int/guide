> **原创训练说明：** 以下三组均为 guide 项目编写的虚构模拟，题目、角色与规模用于训练，不对应真实公司、真实候选人或真实面试记录，也不构成“某公司必考题”。原站公开介绍及其历史宣传文字保留在文末。

## 怎么使用这些模拟

找一位同伴扮演面试官，或者录音自答。每组五题，建议 35–45 分钟；先完整回答，再看参考回答。每题按四项各记 1 分：结论正确、机制清晰、说出失败边界、提出验证方法；每组满分 20 分。忘记术语但能准确解释机制可以得分，反复堆中间件名不能代替答案。

下面的“参考回答”展示表达结构。谈自己的项目时，应替换为真实职责与证据；只在本地验证过就明确说本地验证，没做过的部分按设计推演来讲。

## 模拟一：校招 Java 后端，围绕课程订单项目

**训练设定：** 候选人实现过一个本地课程订单练习项目，包含登录、课程列表、下单和订单查询。未上线，没有真实商业成交数据。面试官关注基础、本人职责和验证能力。

### 1. 先介绍你实际完成的部分

**面试官：** 用两分钟介绍项目，重点说你做了什么、遇到什么问题。

**参考回答：** “这是用于学习的课程订单项目。我实现了下单接口、订单查询和超时取消，使用关系数据库保存订单状态。最初我把库存查询和扣减拆成两步，并发请求可能同时看到还有库存。我改成事务中的条件扣减，并检查更新行数，再写订单。我会用固定库存、多线程请求和数据库核对来验证不超卖；没有真实线上流量，因此不会声称支持生产级秒杀。”

**追问：** 如果目前只有顺序调用测试，能证明并发安全吗？不能。顺序成功只证明正常路径；还应同时启动竞争请求，并在响应超时、事务回滚和重复请求情况下检查库存与订单关系。

**复盘动作：** 画出你自己的请求链路，标出本人实现和框架提供的部分；准备一份真实测试输入、执行结果与约束检查。参考[项目面试准备](./backend-project-interview-guide.md)。

### 2. 同一用户连续点击下单怎么办

**参考回答：** “客户端禁用按钮只能改善交互，不能保证幂等。服务端要求客户端为这次下单生成请求 ID，按用户和请求 ID 建唯一键，并绑定请求摘要。同键同请求返回原订单，不同请求内容拒绝复用。创建订单、库存扣减和幂等记录放在同一事务里；如果已提交但响应丢失，重试查询原结果。”

**追问：** 把请求 ID 存进 Redis，过十秒过期可以吗？这取决于业务重试期限，而且缓存丢失会失去约束。订单这种长期事实应由数据库唯一键或同等可靠记录兜底，过短去重窗口会让迟到重试创建新订单。

**复盘动作：** 同一个请求并发提交十次，结果应只对应一个订单；再用同一个键改变商品参数，确认返回冲突。参考[幂等设计](../high-availability/idempotency.md)。

### 3. 订单列表为什么慢，怎样设计索引

**面试官：** 页面按用户查最近订单，SQL 包含 `user_id = ?`，按创建时间和 ID 倒序，每页 20 条。

**参考回答：** “先确认执行计划与实际扫描行数，不能只看到慢就加缓存。考虑 `(user_id, created_at, id)` 索引，使用户过滤和稳定排序匹配。深分页用上一页最后一条的 `(created_at, id)` 做游标条件，避免不断跳过大量 offset。选择字段不要无条件 `SELECT *`，但是否建覆盖索引要权衡索引大小和写入成本。”

**追问：** 只用创建时间做游标是否足够？若同一时间有多条订单会漏项或重复，所以要加入唯一 ID 打破同值。游标还必须绑定原过滤条件，不能拿用户 A 的游标查用户 B。

**复盘动作：** 构造大量同时间戳订单和深页数据，对比扫描行数、排序步骤及翻页完整性。不要把学习样本的耗时写成线上提升比例。

### 4. 为什么给内部方法加事务仍没有回滚

**参考回答：** “常见代理模式中，同一个对象内部直接调用另一个带事务注解的方法，可能没有经过事务代理。先检查实际 Bean、调用路径和事务管理器，再检查异常有没有被吞掉及默认回滚规则。我会把需要事务边界的方法放在明确的服务入口，通过容器管理的代理调用，避免仅靠注解名称判断。”

**追问：** 方法里启动新线程后还能用原事务吗？一般不能自动继承。异步操作需要自己的事务边界，或由本地事务写出事件，提交后再处理。原事务回滚时，已发出的外部消息也不会自动收回。

**复盘动作：** 给一次真实数据库写入制造异常，检查数据是否回滚；再比较外部调用与自调用。参考[Spring 事务](../system-design/framework/spring/spring-transaction.md)。

### 5. 写出 LRU 缓存的思路并解释复杂度

**参考回答：** “用哈希表定位节点、双向链表维护访问顺序。get 命中后把节点移到最近使用端；put 更新已有节点或插入新节点，超容量时移除最久未用节点，并同步删除哈希表条目。哈希查询在常见条件下平均 O(1)，链表移动和删除 O(1)。容量为零、重复键、尾节点更新和空表都要测试。”

**追问：** 换成 ConcurrentHashMap 就线程安全了吗？不够，表与链表之间需要维护共同不变量，多个步骤必须在同一同步策略下完成。课程代码可以用一把锁先保证正确，生产缓存优先评估成熟实现。

**复盘动作：** 对容量 2 执行 `put(1), put(2), get(1), put(3)`，最终应淘汰 2，再覆盖重复更新和容量 0。完整实现可对照 [LRU 缓存](../cs-basics/data-structure/lru-cache.md)。

### 本组复盘

校招回答的重点是把做过的内容解释清楚。若第 1 题全是框架名字、第 2 题只能说“加锁”、第 4 题只背注解定义，就分别补职责证据、并发原子边界和真实回滚实验。评分达到 16 分后，再缩短到每题两分钟，训练表达密度。

## 模拟二：社招后端，支付回调与故障排查

**训练设定：** 假设系统向第三方支付渠道发请求，通过回调或主动查询确认结果。以下数据和故障均为推演设定，不能作为个人工作成果使用。面试官关注不确定结果、可恢复性与工程证据。

### 1. 支付请求超时了，能直接重试吗

**参考回答：** “超时只表示我没拿到结果，渠道可能已经扣款。先用固定商户单号查询或用同一幂等业务号重试，不能重新生成订单号再次付款。本地把状态留为处理中，记录重试次数和下一次查询时间；确认成功或明确失败再迁移状态。长时间未知进入对账和人工处理。”

**追问：** 为什么不先退款再试？因为尚不知道是否扣款，退款本身也可能失败或结果未知。多个相反动作会扩大不确定性，必须先确定原交易事实。

**验证动作：** 在“渠道成功、本地收响应前”中断连接，确认恢复后只产生一笔实际支付。评分时若答案是“catch 异常就再调用三次”，本题不能得正确性分。

### 2. 消费者扣款成功后、确认消息前崩溃怎么办

**参考回答：** “消息会再次投递，这是正常恢复路径。若副作用是本地数据库写入，把消费去重记录与业务变化写在同一事务，唯一键阻止再次执行。若是外部渠道，使用渠道支持的同一业务幂等号，并能查单；本地收件表不能单独证明外部操作没有执行。”

**追问：** 先在 Redis 标记已处理再扣款可以吗？标记后崩溃会漏处理；扣款后才标记又会重复。要把原子边界说清楚，无法跨系统原子提交时采用状态机和对账，而不是调换两行代码声称解决。

**验证动作：** 在副作用前、提交后、确认前分别注入中断，最终只记一笔有效流水。参考[消息队列](../high-performance/message-queue/message-queue.md)。

### 3. 峰值 1000 QPS，平均耗时 200 ms，需要多少线程

**参考回答：** “在稳定系统中，平均在途请求量可估为吞吐乘平均耗时，示例约为 200，但这不是直接配置 200 个线程的结论。我要拆分 CPU 时间、I/O 等待、下游最大并发和连接池限制，再确定线程与排队预算。P99 耗时上涨、重试放大和突发流量会使稳态估算失效，必须压测并观察饱和点。”

**追问：** 数据库连接只有 50 个，还能把线程池改到 500 吗？增加线程可能只增加等待和内存，并不提升数据库处理能力。应限制并发、缩短占用、减少请求成本，或经过证据支持后扩容下游。

**验证动作：** 保持同一请求分布逐档增加并发，记录吞吐、P95/P99、错误率和队列等待。数据不齐全时明确说明估算假设，不编造“调参后提升 80%”。

### 4. 分布式锁续租了，为什么仍会重复操作

**参考回答：** “线程可能发生长暂停或与锁服务断联，锁到期后新执行者获得锁，旧执行者恢复时仍以为自己有权限。持有者令牌可以避免误删别人的锁，但不能防止旧执行者写业务资源。严格场景要让资源端校验 fencing token 或通过版本条件更新拒绝旧操作，业务本身还要幂等。”

**追问：** 把 TTL 改成一天行不行？这只是改变故障窗口并增加恢复时间，不解决持有者失效的问题。锁时间应根据业务及恢复策略设置，不能用极长 TTL 代替正确性设计。

**验证动作：** 暂停旧持有者直到锁过期，让新持有者成功写入，再恢复旧持有者，验证后者不能覆盖新结果。参考[分布式锁](../distributed-system/distributed-lock.md)。

### 5. 发布后延迟突增，你先做什么

**参考回答：** “先看影响范围、错误率和业务风险，满足回滚条件时按既定流程回滚并保留证据。对比发布前后的请求量、慢调用、线程池、连接池和 GC；用 Trace 找耗时段，用多次线程样本区分计算、锁等待和 I/O。形成可验证假设后做单变量验证，避免同时调十个参数失去因果关系。”

**追问：** CPU 不高能排除应用问题吗？不能，无界排队、死锁、连接耗尽、外部超时都可能让 CPU 不高而延迟很差。

**验证动作：** 在隔离环境复现慢下游或锁竞争，确认监控能区分症状，并验证超时、隔离和回滚能恢复。参考[JVM 排查工具](../java/jvm/jdk-monitoring-and-troubleshooting-tools.md)。

### 本组复盘

把每题的“未知状态”写出来：未知是否扣款、未知是否执行、未知瓶颈在哪里。好的回答会保留未知，设计查询和恢复；差的回答会把超时直接等价成失败。若答题时声称“绝对不丢”“恰好一次”，继续追问承诺在哪个边界内成立。

## 模拟三：系统设计面，短链与站内消息

**训练设定：** 设计一个允许创建、撤销、统计短链的平台，并在后台向创建者发送审核消息。假设每日 1000 万跳转、100 万新链接，保存一年；峰值倍率和可用性目标需主动澄清。

### 1. 先澄清需求并做容量估算

**参考回答：** “我先确认短链能否修改或撤销、是否私密、统计允许多大延迟，以及数据保存期限。1000 万日跳转平均约 116 QPS；若暂取峰均比 20，峰值约 2320 QPS。一年新增约 3.65 亿条链接。单条记录大小先实测，容量还包括索引、副本和日志，不能只把 URL 字节乘行数。”

**追问：** 为什么不立即做分库分表？先看单库容量和读写瓶颈、增长速度与可维护性。保留可迁移的主键和分区策略，不等于第一天就引入多个数据库。

**验证动作：** 用具有真实长度分布的 URL 测表和索引占用，生成冷热分布的读写压测，不只测试全部命中缓存的均匀请求。

### 2. 短码怎样生成，碰撞和越权如何处理

**参考回答：** “可用唯一 ID 的 Base62 编码，或者随机短码加数据库唯一约束和有限重试。表保存 code、target、owner、expires_at 和 status。创建与修改都验证所属用户，跳转只支持约定协议。私密链接仍要鉴权，难猜的短码不是权限体系。”

**追问：** 同样的 URL 必须生成同一个短码吗？不一定，不同所有者可能要独立有效期、统计和撤销。是否去重是产品规则，不能直接用 URL 哈希代替业务主键。

**验证动作：** 人为制造碰撞、跨用户修改、危险协议和超长地址。若服务要抓取目标内容，还要验证 SSRF 防护及重定向链。

### 3. 缓存、撤销和统计怎样协调

**参考回答：** “跳转先查缓存，未命中查事实库并回填；撤销提交后发送失效事件，缓存 TTL 限定旧结果存活时间。如果产品要求立即撤销，应采用更严格的检查路径，不能只声称删除一次缓存即可。跳转统计异步聚合，统计服务故障不阻断核心跳转。”

**追问：** 浏览器长期缓存永久跳转后还能立即撤销吗？不能可靠召回已经缓存的客户端结果，因此跳转状态码与缓存控制必须与可撤销需求共同设计。

**验证动作：** 在撤销与旧查询回填并发时验证最终状态，分别模拟缓存、事件服务和统计库故障。指标包括核心成功率、撤销延迟与统计迟到量。

### 4. 审核消息未读数为什么不能只用减一

**参考回答：** “消息事实与用户收件箱持久化，`user_id + message_id` 去重。标记已读用条件更新 `unread -> read`，只有首次成功才减少计数；重复点击不再减。WebSocket 只负责提示，断线后按游标补拉。计数缓存可以从事实重建，不应成为唯一来源。”

**追问：** 两台设备同时已读怎么办？它们竞争同一个状态迁移，只能有一次有效变化；其他设备收到同步结果。群发公告和个人消息的数据模型还要根据规模区分。

**验证动作：** 重复投递、两设备同时已读、落库后推送前崩溃和清空计数缓存，检查可恢复性与一致性。

### 5. 这个系统怎样验证恢复能力

**参考回答：** “列出故障矩阵：应用重启、缓存不可用、数据库主从切换、消息重复和消费者崩溃。先定义恢复时间与可接受丢失范围，再执行故障演练。备份必须做恢复验证，复制不能代替备份。对所有已确认创建的链接，我要能说明其持久化位置以及故障后如何找回。”

**追问：** 三个副本是不是就不会丢数据？不是，还要看复制确认、持久化配置、故障类型和备份。多个副本也可能一起复制误删除。

**验证动作：** 在隔离环境恢复备份，核对样本与总量；记录恢复耗时和缺失窗口。没有执行的演练应列为待验证，不能写成已经具备灾备能力。完整答案参见[系统设计场景题](../system-design/system-design-questions.md)。

### 本组复盘

将方案缩成一张图：入口、事实库、缓存、异步事件和恢复器。逐条标注哪些是强一致约束，哪些允许延迟，以及每个异步动作依靠什么重新执行。讲清这张图，比额外列出十种中间件更能体现设计能力。

## 把模拟结果变成下一周复习计划

| 本轮暴露的问题 | 复习动作 | 完成证据 |
| --- | --- | --- |
| 概念混淆 | 重读对应正文，再脱离材料解释一个反例 | 录音中能区分两个概念与边界 |
| 只会正常路径 | 为原方案增加重复、超时、并发和崩溃用例 | 不变量检查通过，并保留失败前后的证据 |
| 方案堆砌 | 从最短链路出发，逐个说明新增组件解决什么 | 去掉任何组件时能指出具体影响 |
| 说不清个人职责 | 列出本人代码、验证动作和未负责部分 | 有真实提交、测试或设计记录可核对 |
| 把推演说成成果 | 把“已实现、已验证、设计中”分别标明 | 面试回答与现有证据一致 |

三天后复测本轮低于 3 分的题，一周后换一组业务场景重新回答。需要更细的基础检查时，使用[28 题自测与评分](./self-test-of-common-interview-questions.md)。

在 **[《Java 面试指北》](../zhuanlan/java-mian-shi-zhi-bei.md)** 的 **「面经篇」** ，我分享了 30+ 篇高质量的 Java 后端面经，有校招的，也有社招的，有大厂的，也有中小厂的。

相比于牛客网或者其他网站的面经，《Java 面试指北》中整理的面经质量更高，并且，我会提供优质的参考资料。

有很多同学要说了：“为什么不直接给出具体答案呢？”。主要原因有如下两点：

1. 参考资料解释的要更详细一些，还可以顺便让你把相关的知识点复习一下。
2. 给出的参考资料基本都是我的原创，假如后续我想对面试问题的答案进行完善，就不需要挨个把之前的面经写的答案给修改了（面试中的很多问题都是比较类似的）。当然了，我的原创文章也不太可能覆盖到面试的每个点，部分面试问题的答案，我是精选的其他技术博主写的优质文章，文章质量都很高。
