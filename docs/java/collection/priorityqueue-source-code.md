## 先记住结论

**PriorityQueue 是由数组表示的二叉堆，队头始终是当前比较规则下的最小元素。** 使用自然顺序时常被称为小顶堆，传入逆序比较器即可把最大的元素放在队头。它维护的是“父节点不大于孩子”的局部约束，因此 `poll()` 会按优先级取出元素，迭代器却不保证有序。

它不允许 `null`，允许重复值，不保证相同优先级元素的先后次序，并且不是线程安全容器。需要多个线程协作时，不能仅凭“入队看起来只改一个位置”就无锁共享。[Java 21 API 契约](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/PriorityQueue.html)

| 操作                       | 常见复杂度    | 原因                                                       |
| -------------------------- | ------------- | ---------------------------------------------------------- |
| `peek()`                   | O(1)          | 查看数组第一个元素                                         |
| `offer()`                  | 通常 O(log n) | 沿父节点路径上浮；触发数组扩容的一次操作还要复制 O(n) 元素 |
| `poll()`                   | O(log n)      | 删除堆顶后沿孩子路径下沉                                   |
| `contains(x)`、`remove(x)` | O(n)          | 数组没有按所有元素建立搜索索引，需要寻找目标               |
| 从普通集合构建堆           | O(n)          | 从最后一个非叶子节点开始自底向上调整                       |

## 数组为什么能表示树

将完全二叉树按层从左到右放入数组。零起始下标 `i` 的父节点为 `(i - 1) / 2`，左孩子为 `2 * i + 1`，右孩子为 `2 * i + 2`。根节点没有父节点，推导时必须把这一边界单独处理。

```text
数组：[2, 5, 3, 9, 7, 8]

          2
        /   \
       5     3
      / \   /
     9   7 8
```

这个数组是合法的小顶堆：每个父节点都不大于孩子，但数组里的 5 出现在 3 前面。因此 `for-each` 遍历不能被当成升序输出。需要有序消费时反复 `poll()`；需要保留原队列时，可复制成另一个优先队列后取出，或复制到数组并使用相同的比较规则排序。

在 OpenJDK 实现里，重点看 `queue` 数组、`size`、`comparator` 和 `modCount`。前两个表示实际内容及大小，比较器决定优先级，修改计数用于迭代器的并发修改检查。fail-fast 只是尽力发现错误用法，不是同步机制，也不能成为业务正确性的依据。[OpenJDK 21 PriorityQueue 源文件](https://raw.githubusercontent.com/openjdk/jdk21u/master/src/java.base/share/classes/java/util/PriorityQueue.java)

## offer：先追加，再沿路径上浮

假设当前堆为 `[2, 5, 3, 9, 7, 8]`，现在插入 1。新元素先占据下标 6，对应父节点下标 2，父值为 3；因为 1 更小，3 向下移动。接着比较根值 2，2 也向下移动，最后把 1 放入根位置，得到 `[1, 5, 2, 9, 7, 8, 3]`。

这里不需要把整个数组重新排序，因为除了新元素到根的一条路径，其他父子关系都没变化。每次走上一层，所以比较次数最多与树高同阶。实现通常采用“挖坑填值”减少交换次数：父值向下搬，最后只写一次待插入值。

扩容与上浮是两个问题。容量不足时先分配更大的数组并复制原元素，之后才有空间放入新元素。不要把某个 JDK 的扩容比例当成 Java API 的永久承诺。对已知数据规模，可以设置适当初始容量以减少复制，但过度预分配也会浪费内存。

## poll：末尾元素补到根，再沿路径下沉

在 `[1, 5, 2, 9, 7, 8, 3]` 上删除队头 1，取出末尾 3，清空尾槽以便引用释放，然后修复根位置。根的两个孩子是 5 和 2，应选择较小的 2 向上填补，而不是只与左孩子比较；3 最终落在合适的位置，得到 `[2, 5, 3, 9, 7, 8]`。

为什么一定要选较小的孩子？如果把较大的孩子提升为父节点，就可能仍然大于另一个孩子，破坏堆约束。`siftDown` 每一步只需要在两个孩子中选小，再决定待放值是否已经可以停下。

删除任意对象更复杂：先线性寻找，再用末尾元素填坑，修复可能向下，也可能向上。因此 `remove(Object)` 不能宣传成 O(log n)。重复对象还涉及 `equals` 语义，与比较器判断“优先级相同”是两个不同概念。

## heapify 为什么是 O(n)

把 n 个元素逐个 `offer()`，上界是 O(n log n)。但已拿到完整数组时，可以从最后一个非叶子节点向根执行下沉。靠近底层的节点很多，却几乎不用移动；靠近根的节点少，才可能移动较多层。

粗略计数：约一半节点是叶子，代价为零；四分之一节点最多下沉一层；八分之一节点最多下沉两层。总工作量可写成与 `n * (1/4 + 2/8 + 3/16 + ...)` 同阶，这个级数收敛，所以整体是 O(n)。理解这个推导，比记住“建堆是线性”更有助于回答追问。

## 实战：保留数据流中最大的 K 个数

要保留最大的 K 个数，使用容量受业务逻辑限制的小顶堆：堆顶恰好是当前入选者中最弱的一位。新值不比堆顶大时可忽略；更大时淘汰堆顶。注意 `PriorityQueue` 本身没有容量上限，这个 K 限制由代码保证。

```java
import java.util.ArrayList;
import java.util.Comparator;
import java.util.List;
import java.util.PriorityQueue;

public class TopKDemo {
    static List<Integer> largestK(int[] values, int k) {
        if (k <= 0) return List.of();
        PriorityQueue<Integer> heap = new PriorityQueue<>();
        for (int value : values) {
            if (heap.size() < k) {
                heap.offer(value);
            } else if (value > heap.peek()) {
                heap.poll();
                heap.offer(value);
            }
        }
        List<Integer> answer = new ArrayList<>(heap);
        answer.sort(Comparator.reverseOrder());
        return answer;
    }

    public static void main(String[] args) {
        System.out.println(largestK(new int[]{7, 2, 9, 9, 4}, 3));
        // 预期：[9, 9, 7]，本题保留重复值。
    }
}
```

处理 n 个元素的堆操作成本为 O(n log K)，额外空间 O(K)，最后对结果排序还需要 O(K log K)。如果业务要求“最大的 K 个不同值”，必须另加去重语义；如果要求前 K 个订单，应该保存订单及比较字段，而不是只保存金额。

## 比较器、可变对象与稳定性陷阱

整数比较不要写 `a - b`，极值相减可能溢出并反转比较结果，优先用 `Integer.compare(a, b)` 或 `Comparator.comparingInt(...)`。比较关系还应满足传递性，不能根据随时变化的外部状态返回不一致结果，否则算法依赖的顺序就不成立。

对象已经进入队列后，如果直接修改用于比较的优先级字段，队列不会自动重新调整。例如原堆底任务的优先级从 100 改为 1，`peek()` 未必能立刻返回它。可行方式是先移除旧对象、修改后重新入队，或使用不可变任务快照并在出队时跳过失效版本。后者要评估旧条目堆积产生的额外内存。

若同优先级要求 FIFO，比较器应先比优先级，再比入队序号；仅比较优先级无法保证稳定性。序号的生成、并发写入和生命周期也要纳入设计。需要按时间到期消费时，单纯优先队列还缺少等待唤醒机制，应结合调度器或适合的阻塞容器，而不是让线程不停 `peek()` 忙等。

## 自测与参考答案

1. **为什么求最大的 K 个数用小顶堆？** 因为需要快速淘汰入选集合里最小的元素。大顶堆能快速看到最大者，却无法 O(1) 找到应淘汰的最小者。
2. **打印队列得到 `[2, 5, 3]`，实现是否坏了？** 没坏，它满足堆约束。打印和迭代不承诺排序，连续 `poll()` 才按当前比较顺序取出。
3. **`remove(x)` 找到元素后只调整一条路径，为什么仍是线性复杂度？** 查找 x 已经需要 O(n)，后续 O(log n) 修复不会改变总体量级。
4. **多个线程只调用 `offer()` 可以共享普通 PriorityQueue 吗？** 不可以，它们会同时修改数组、大小与堆关系。使用明确的外部同步或适当并发容器，并一起检查容量和背压需求。
