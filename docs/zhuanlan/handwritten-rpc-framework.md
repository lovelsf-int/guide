## 免费学习正文：从请求生命周期设计一个教学 RPC

> **guide 原创补充**：下面是本镜像独立编写的教学方案，不是上游付费教程的复制，也不保证与 `guide-rpc-framework` 当前实现逐类对应。上游开源项目的公开介绍保留在文末；本节中的协议、伪代码和练习均用于解释设计取舍。

一个 RPC 学习项目最重要的产物，是你能够解释请求从创建到结束的每个状态：调用方在哪里等待，服务端在哪里执行，响应丢失时怎么办，超时后哪些资源需要释放。先做单服务单连接的完整闭环，再加入发现与治理，会更容易识别每个组件存在的理由。

## 先定义边界和调用链

把框架分成六个接口：代理将本地方法转换为请求；编解码负责字节与消息；传输负责连接和发送；发现返回候选服务地址；选择策略从候选中选一个；服务目录按允许的服务和方法执行。开始时，发现可以返回固定地址，序列化只支持一种，负载均衡只选择唯一实例。接口稳定后再逐步替换实现。

```text
业务接口 → 代理 → 请求与 deadline → 发现/选择 → 连接
         → 编码与发送 → 服务端解码 → 有界业务执行器
         → 结果编码 → 客户端按 requestId 找到等待者 → 完成
```

服务端只能调用预先登记的服务和方法，不能让客户端通过任意类名执行反射。参数大小、集合深度和字符串长度都要有限制；反序列化格式也应明确允许类型。TLS、身份认证和授权属于部署到不可信网络前必须实现的能力，教学原型未实现时应明确写出边界。

基础知识可以分别阅读[RPC 调用原理](../distributed-system/rpc/rpc-intro.md)、[动态代理](../java/basis/proxy.md)、[序列化](../java/basis/serialization.md)和[SPI](../java/basis/spi.md)，这里集中解决它们连接后的生命周期问题。

## 协议设计：消息边界必须能验证

教学协议可以使用固定大小的头部，包含魔数、版本、消息类型、消息体长度和请求 ID，正文再放服务标识、方法标识、参数与结果。字段宽度、字节序、长度包含范围和上限都写入协议文档，客户端与服务端共同遵守。不要直接把一个 Java 对象的内存布局当作网络协议。

接收方按三个阶段处理：头部不足则等待；头部完整后校验版本、长度和类型；完整正文到达后才反序列化。声明长度超过上限应及时拒绝，不能先分配超大数组再判断。若加入压缩，压缩帧上限和解压后的上限必须分别检查。

TCP 不保留应用消息边界，因此一次写入可能分多次读取，多次写入也可能一起读取；可对照 [Netty 4.x 用户指南的流式传输说明](https://netty.io/wiki/user-guide-for-4.x.html)。本项目的解码测试应按任意字节位置切分一条消息，再验证只产生一个完整请求；同时验证两条连续消息产生两个请求。

## 请求关联：所有终止路径只有一个获胜者

同一连接允许多个请求在途，响应顺序可能与请求顺序不同，因此使用请求 ID 关联等待者。请求 ID 在连接生命周期内不复用，并把映射归属于连接；连接重建时不能让旧响应完成新请求。开始阶段还要限制在途数量，使等待表不会无限增长。

以下是**事件循环伪代码**，用于表达状态转换，不是可直接运行的完整 Java 类。`ownerLoop` 串行管理该连接的等待表，网络事件与定时事件都回到它；完成 Future 的通知由单独的完成执行器承接，防止业务回调阻塞 I/O。真实实现还需处理执行器停机和任务拒绝。

```text
submit(request, deadline, future):
  在 ownerLoop 中：
    若 future 已取消、连接已关闭或 deadline 已到：结束 future 并返回
    若在途数量已到上限：以 OVERLOADED 结束 future 并返回
    分配本连接内唯一 id
    pending[id] = (future, deadline, timer)
    安排到期事件 finish(id, TIMEOUT)
    发送请求；异步写失败时 finish(id, TRANSPORT_ERROR)

finish(id, outcome):
  在 ownerLoop 中：
    entry = pending.remove(id)
    若 entry 不存在：记录晚到/重复事件并返回
    取消 entry.timer；归还在途名额
    将完成 entry.future 的动作交给完成执行器

收到响应：finish(id, response)
调用方取消：finish(id, CANCELLED)
连接关闭：对该连接全部 pending 调用 finish(id, CLOSED)
```

这里真正重要的是先从等待表中取走唯一所有权，再完成等待者。响应、超时、取消、写失败与断连都走同一个出口，因此不会重复归还名额。注册映射与设置定时器也要在同一串行上下文完成，避免“超时先发生、请求后入表”造成泄漏。取消在正式注册前发生时，提交阶段必须再次观察取消状态。

## 超时、重试与业务结果要分开

客户端把一次调用的总预算分给服务发现、获取连接、排队、发送与等待响应。只在 `get()` 上设置超时会漏掉前面的等待。本进程用单调时钟计算剩余预算；跨进程不能直接比较两台机器的单调时钟值。传递相对预算时还要扣除已经消耗的时间，并考虑网络时延，因此它不能替代客户端自己的最终截止时间。

Future 结束只是调用方不再等待，不代表服务端停止或副作用回滚。Java 的 `CompletableFuture.cancel` 也不会因参数为 `true` 就自动中断计算，具体语义见[官方 API](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/concurrent/CompletableFuture.html)。若要支持远程取消，需要额外的取消消息、服务端任务登记和协作停止；即使如此，已提交的数据库事务仍需要业务补偿或结果查询。

重试从只读查询开始练习。对于扣款、发券、创建订单等操作，先定义业务幂等键和重复结果查询，再讨论自动重试。区分“请求尚未发出”“已发出但结果未知”“业务明确拒绝”，不要把三者统一重试。重试次数、退避和总预算一起约束，避免局部重试把下游故障放大。

## 服务发现和 SPI 何时加入

固定地址版本稳定后，再接入 ZooKeeper：服务实例发布临时节点，客户端维护地址快照，监听变化后重新获取最新视图。临时节点与创建它的会话绑定，会话结束时删除；短暂网络断开不等于会话立即过期，参见[ZooKeeper 编程指南](https://zookeeper.apache.org/doc/r3.9.3/zookeeperProgrammers.html)。服务端应在网络监听和业务准备完成后发布地址，停机先停止接入新请求，再等待在途任务或按预算终止。

地址缓存不是健康证明。选择到失效实例后，传输层仍会失败；注册信息恢复也不能代替服务实际就绪。练习至少覆盖会话失效后重新注册、地址列表为空以及监听与重新读取之间发生变化的场景。可以复用[ZooKeeper 实战](../distributed-system/distributed-process-coordination/zookeeper/zookeeper-in-action.md)。

当出现第二种序列化器或选择算法时再加入命名 SPI：启动时发现扩展，校验名称唯一、类型正确、必需扩展存在；调用期间通过已验证的注册表选择。错误配置应在启动阶段清晰失败。不要为了可扩展性允许每次请求加载任意类，也不要把配置名称直接当作可执行代码。

## 实验矩阵和完成标准

| 实验 | 必须检查的结果 |
| --- | --- |
| 100 个并发请求乱序响应 | 每个 Future 得到自己的结果，等待表最终为空 |
| 响应与超时竞争 | 仅一个结果生效，名额只归还一次 |
| 超时后响应晚到 | 丢弃晚到响应，不关闭仍供其他请求使用的连接 |
| 写失败或连接关闭 | 相关等待者都结束，计时器和映射被清理 |
| 半帧、合并帧、超长帧 | 正确拆帧或明确拒绝，不无限分配内存 |
| 服务端耗时与过载 | I/O 线程保持可用，有界业务队列按契约拒绝 |

先用确定性测试控制响应、时间和断连，再进行真实进程间测试。完成标准是上述异常路径都留下记录，并能指出原型仍缺少哪些治理能力。简历中可写清自己实现的协议与清理机制；只有经过实际压测才能写吞吐和延迟，测试数量也以自己的运行结果为准。

## 一次 RPC 调用经过了什么

![Guide RPC Framework 整体架构](https://oss.javaguide.cn/github/javaguide/distributed-system/rpc/guide-rpc-framework-architecture.webp)

以 `@RpcReference` 注入的服务接口为例，一次调用会经过这些环节：

```text
本地接口调用
    ↓
JDK 动态代理组装 RpcRequest
    ↓
ZooKeeper 服务发现
    ↓
一致性哈希选择服务实例
    ↓
建立或复用 Netty Channel
    ↓
协议编码、序列化与压缩
    ↓
服务端拆帧、解码并执行目标方法
    ↓
响应按 requestId 完成对应 CompletableFuture
```

教程不会停在“客户端发送请求、服务端返回结果”这一层。协议字段怎样排列、服务端为什么不能在 I/O 线程里执行耗时方法、请求从排队到收到响应如何共用一个超时预算，这些问题都会结合当前代码说明。

## 这套教程怎么讲

教程先用 Socket 和 JDK 动态代理搭出最小调用链，再逐步换成 Netty、自定义协议、可插拔序列化和 ZooKeeper。读者可以看到每次改造解决了哪个问题，而非直接面对一套已经组装好的代码。

源码分析部分按真实调用顺序展开。客户端怎样生成请求、服务发现怎样选择地址、编解码器怎样处理消息、服务端怎样执行方法、响应怎样完成 Future，都能在文章和代码之间对应起来。

后面的 SPI、负载均衡和测试章节继续处理扩展与失败场景。除了正常调用，也会讨论重复 `requestId`、响应晚到、请求超时、连接提前关闭、非法协议帧和 ZooKeeper 会话失效。

运行项目所需的环境、启动顺序和第一次 RPC 调用继续放在项目 README 的“快速开始”中维护，不再单独拆一篇重复文章。

- 多个并发请求复用一条 Channel 时，响应怎样找到对应的 `CompletableFuture`？
- 请求超时从哪个时间点开始计算，为什么要覆盖排队和服务发现？
- 自定义 SPI 与 JDK `ServiceLoader`、Dubbo SPI 分别有什么差异？
- ZooKeeper 临时节点、CuratorCache 和会话恢复各自解决什么问题？
- 一致性哈希为什么需要虚拟节点，服务实例变化时哪些请求会重新映射？
- 服务端为什么要把业务执行移出 Netty I/O 线程，同一 Channel 上的方法能否并行？
- 这个框架距离生产可用还缺哪些能力，应该先补哪一项？

如果这些问题只能背结论，建议回到对应章节对照代码再走一遍。

## 适合谁学习

- 已经学过 Java 基础、集合、反射和多线程，想把这些知识放进一个完整项目中使用。
- 接触过 Netty 或 ZooKeeper，但对它们在 RPC 调用链里的职责还比较模糊。
- 正在准备 Java 后端校招、社招，希望增加一个能深入讲协议、网络和分布式协作的项目。
- 平时会使用 Dubbo、Feign 等远程调用工具，想继续理解代理、协议、注册发现和响应关联是怎样实现的。
- 准备阅读 Dubbo、Netty 等框架源码，希望先用一个体量较小的项目建立整体认识。

第一次接触 RPC 没关系，但最好已经掌握 Java 基础语法、Maven 和基本的客户端/服务端概念。教程不会花大量篇幅重复这些前置知识。

## 建议学习顺序

1. 按项目 README 准备 JDK 25、Maven 3.9 和 ZooKeeper 3.9.5，先跑通服务端与客户端。
2. 阅读前 8 篇教程，自己完成 Socket、代理、Netty 和 ZooKeeper 的最小实现。
3. 对照第 9～14 篇阅读当前源码，至少亲手改造一个扩展点，例如新增序列化器或负载均衡策略。
4. 执行 `mvn verify`，再补一个超时、断连或非法帧测试，确认自己能解释失败后的资源清理。
5. 最后整理简历并准备追问。没有亲手验证过的能力，不写进项目经历。

## 常见问题

### 项目代码需要付费吗？

不需要。GitHub 和 Gitee 仓库中的代码完全免费开源，没有 Pro 版本。

### 配套教程在哪里阅读？

配套教程是 JavaGuide 知识星球内部小册，通过语雀文档在线阅读，不单独对外出售。

教程以文字、源码分析和技术配图为主。阅读时可以直接在文章与代码之间切换，也方便后续检索某个协议字段、类或测试场景。
