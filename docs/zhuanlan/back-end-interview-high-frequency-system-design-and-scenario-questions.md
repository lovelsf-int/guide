## 用约束、状态与证据组织系统设计

> 通过报表导出任务练习需求约束、容量估算、状态机与故障恢复。短链、秒杀、登录、上传等具体案例可继续阅读[系统设计常见面试题](../system-design/system-design-questions.md)。

系统设计题的有效答案，应让听者知道：你要保证什么、怎样完成一次操作、哪里可能失败、如何判断系统仍然正确。先画十种中间件通常不能解决这些问题。下面以“用户提交一个大报表导出任务”为独立练习，展示一套可以迁移到订单、通知和文件处理的分析方法。

## 第一步：把模糊需求变成五条契约

假设产品要求：用户提交筛选条件，稍后下载报表；同一用户重复点击不会创建相同任务；只能下载自己有权访问的数据；任务可取消；失败后可以重试。继续明确边界：导出反映提交时的数据还是执行时的数据，文件保留多久，允许多长排队时间，单个租户最多同时运行几个任务。

这些问题决定设计。若允许执行时快照，可以保存查询条件后异步执行；若要求提交时精确快照，就需要版本边界、快照表或数据库支持，不能只记录一个时间戳便声称所有关联数据一致。本文选择“执行开始时确定导出视图”，将其写入任务记录和页面说明，避免用户把正在变化的数据误认为静态账单。

先写不变量：任务只属于一个租户；终态不被旧执行者覆盖；一个幂等键最多对应一个任务；只有已完成且未过期的任务允许下载；取消后的任务不得再发布为成功。每项不变量都要找到数据库条件或鉴权检查，不能只依赖前端按钮。

## 第二步：估算最小资源需求

假设一份报表有 100 万行，序列化后每行平均 200 字节，那么原始内容约 200 MB，尚未计入格式、索引、临时文件与副本。若希望两分钟写完，平均有效写入速率至少约 1.67 MB/s；这不是系统总吞吐承诺，因为查询、转换和网络阶段可能更慢。若同时运行 20 个任务，总读写压力需要按并发叠加。

由此得到两个具体选择：分批游标读取，避免把 100 万行装入 Java 堆；按租户和系统总量限制并发，防止报表挤占线上请求的数据库连接。批大小不是越大越好，应结合单行尺寸、连接占用与取消响应速度测量。一个只有平均耗时的压测报告不够，需要记录 P95、失败率、数据库负载和峰值内存。

## 第三步：设计任务模型和事务边界

可以从下面的概念模型出发；字段类型和索引需结合实际数据库调整。

```text
export_job(
  id, tenant_id, user_id, idempotency_key,
  query_spec, view_version, status,
  attempt, lease_until, object_key, expires_at, error_code
)
UNIQUE(tenant_id, user_id, idempotency_key)

outbox(id, aggregate_id, event_type, payload, published_at)
```

创建任务和写入 outbox 放在同一数据库事务中。提交成功后，后台发布器发送任务事件；发送成功但标记失败时可能重复发布，因此消费者必须按任务状态幂等领取。`query_spec` 要保存经过授权和白名单校验的结构化筛选条件，不能存用户拼接的 SQL。幂等键重复但参数不同，应拒绝并提示冲突。

消费者通过条件更新将 `PENDING` 或可恢复的过期 `RUNNING` 任务领取为当前执行代次，增加 `attempt` 并设置租约。随后分批读取数据，写入该代次专属的临时对象。结束时只有满足 `status = RUNNING AND attempt = 自己的代次` 的执行者才能把对象地址写入任务并转成 `SUCCEEDED`。受影响行数为零意味着已失去发布资格，必须清理临时对象。

为什么只有租约还不够？一个暂停很久的旧进程可能在租约过期后恢复，和新进程同时写结果。执行代次让最终状态更新识别旧执行者；对象路径也带代次，避免旧任务覆盖新文件。若某个外部存储不能验证代次，就使用不可变对象加数据库条件发布，读者只通过数据库中被正式发布的对象访问结果。

## 第四步：逐条推演失败

| 故障注入 | 正确结果 | 需要的机制 |
| --- | --- | --- |
| 提交成功后发布进程退出 | 任务以后仍能被发出 | 同事务 outbox 与重扫 |
| 一条消息消费两次 | 只允许有效代次执行和发布 | 条件领取、状态机 |
| 旧进程暂停后恢复 | 不能覆盖新代次结果 | 代次校验、不可变对象 |
| 用户中途取消 | 状态先成为取消，后续成功更新失败 | 条件转换、分批检查 |
| 对象写入成功但数据库提交失败 | 文件暂时不可见，随后被回收 | 临时对象标识与垃圾回收 |
| 权限在排队期间被撤回 | 执行和下载时再次授权 | 服务端权限检查 |

任务取消是一项业务状态变更，线程中断只是尽快停止工作的协作信号。外部查询或对象上传可能已经执行，不能凭 `cancel()` 断言资源被撤销。对于确定失败与结果未知要分开记录，重试策略必须知道上次是否可能已经发布。通用原理见[超时与重试](../high-availability/timeout-and-retry.md)、[接口幂等性](../high-availability/idempotency.md)和[分布式事务](../distributed-system/distributed-transaction.md)。

## 第五步：把方案变成验收表

练习不要求一开始接入复杂调度平台。可以先用关系数据库、一个消费者和对象存储接口实现闭环，再增加队列与多实例。首次运行保存三份证据：同一幂等键并发提交只生成一条任务；杀死消费者后任务可以恢复且没有两个成功结果；撤销下载权限后即使知道任务 ID 也拿不到对象。

进一步加入 10 万行测试数据，观察不同批大小的峰值内存与数据库占用。验收目标由你事先设定，例如在指定开发机上内存不随总行数线性增长，取消能在一个批次结束后被观察到。不要把这个条件直接写成生产 SLA，也不要将静态代码检查当作故障恢复验证。
