## 沿着一个问题读懂框架源码

> 沿着具体问题阅读 Spring Boot、Netty 与 Dubbo 源码。先锁定项目的依赖版本，再寻找对应实现。

源码阅读的起点可以很小：“为什么这个 Bean 出现了”“一条消息为什么被拆成两次回调”“调用失败后是谁发起第二次请求”。带着这类可观察的问题进入框架，比从仓库第一个包开始顺序读，更容易建立因果关系。阅读结果应包含一个具体假设、一条调用链和一个能推翻假设的实验。

## 建立一张源码证据卡

先记录依赖坐标、确切版本、源码 tag、JDK 和启动参数。文档里的类名只能帮助定位，最终以该版本实际执行路径为准。IDE 附加源码时检查二进制和源码版本一致，否则断点位置看似正确，控制流却可能对不上。

每次只研究一个问题，证据卡可以这样填写：

```text
问题：为什么添加自定义组件后，默认组件不再创建？
预期：自动配置先识别条件，再决定是否注册默认 Bean。
入口：启动应用；查看条件评估报告。
观察点：候选配置、条件结果、BeanDefinition、实例创建。
反例：去掉自定义 Bean 或让它不在扫描范围内。
结论：记录观察到的事实、版本以及仍未确认的分支。
```

把“读到的方法”与“运行经过的方法”分开记录。静态搜索能告诉你可能存在的分支，断点和测试才能证明当前配置走了哪条分支。一次成功调用也不能证明失败恢复，后者要单独构造条件。

## Spring Boot：用条件变化追踪自动配置

从一个空应用开始，定义业务接口 `GreetingService`，然后设计默认实现只在用户没有提供实现时创建。先写出三种预期：没有自定义 Bean 时使用默认实现；有一个自定义 Bean 时默认实现退让；用户 Bean 没进入应用上下文时不能被条件识别。

以下代码只是条件装配的最小教学片段，需放到能被当前版本发现的配置类中；它不是完整 Starter 的发布配置。

```java
@Configuration(proxyBeanMethods = false)
class GreetingConfiguration {
    @Bean
    @ConditionalOnMissingBean(GreetingService.class)
    GreetingService defaultGreeting() {
        return name -> "Hello, " + name;
    }
}
```

实验重点不是打印一行问候语，而是回答“条件在哪个阶段评估”“评估时哪些 Bean 定义已经可见”。配置顺序会影响条件判断，正式自动配置应遵循相应版本的导入和排序约定。Spring Boot 官方支持用 `--debug` 查看条件报告；自动配置会结合 classpath 和用户配置决定是否应用，详见[自动配置说明](https://docs.spring.io/spring-boot/reference/using/auto-configuration.html)。

接着沿启动边界向内阅读：`SpringApplication.run` 启动应用，创建和准备上下文，再刷新上下文；不要把“扫描到了类”“注册了定义”和“创建了对象”混成同一件事。以 [SpringApplication API](https://docs.spring.io/spring-boot/api/java/org/springframework/boot/SpringApplication.html)确认顶层职责，再进入自己所用版本的源码。具体配置导入路径、包名与内部类可能随版本变化，不能把 Spring Boot 2.1 的截图当作所有版本都相同的证据。

**练习与验收**：分别让默认 Bean 存在、让自定义 Bean 替代它、让自定义配置不被扫描。保存三份条件报告，说明每次命中的条件。再加入两个同类型用户 Bean，解释歧义发生在什么位置以及如何通过明确选择消除歧义。更细的启动流程见[Spring Boot 核心源码](../system-design/framework/spring/springboot-source-code.md)与[自动装配原理](../system-design/framework/spring/spring-boot-auto-assembly-principles.md)。

## Netty：先观察字节，再看事件传播

为一个回显服务定义“长度字段 + 消息体”协议。发送两条消息 A 和 B，刻意分三次写出：A 的前半段、A 的后半段加 B 的头部、B 的剩余部分。TCP 提供字节流，读取回调不保证与写入次数对应；这一事实及消息拆帧问题可对照 [Netty 4.x 用户指南](https://netty.io/wiki/user-guide-for-4.x.html)核查。

调试时记录五项信息：当前线程、可读字节数、读指针、输出消息数、消息关联 ID。沿着接收、累积、拆帧、解码、业务处理和出站写回画一条链，不需要一开始读懂全部 EventLoop 实现。若首次输入不足一帧，正确表现是保留所需数据并等待后续输入，而不是把半个业务对象交给 Handler。

然后注入一个慢业务：让业务处理暂停一段时间，观察同一事件循环负责的其他连接是否受影响。再把阻塞业务提交到有界执行器，对照延迟和拒绝行为。线程迁移后还要重新检查消息顺序、上下文传播以及共享 Handler 的状态安全；“换成线程池”本身不能证明问题解决。

内存阅读从所有权入手：谁接收 `ByteBuf`、谁保留它、谁最终释放。消费后不再向下传播的消息和继续传播的消息，责任不同；跨异步边界更要核对引用计数规则。不要在所有 Handler 里机械地加 `release()`，那可能把泄漏变成重复释放。可先阅读站内[Netty 原理](../system-design/framework/netty.md)建立术语，再用对应版本的示例验证。

**练习与验收**：用内存通道测试或等价测试工具覆盖单帧、半帧、两帧合并、超长声明长度和连接提前关闭。每个用例检查输出数量与资源释放，不只检查是否抛异常。你应该能够说明为何小流量下“看起来一直正常”的代码仍可能在消息边界上出错。

## Dubbo：沿调用模型分清代理与远程执行

先运行一个服务接口、一个提供者和一个消费者。把入口固定为一次业务方法调用，逐层区分接口代理、集群选择、协议调用与网络传输。Dubbo 官方架构把 `Invoker` 作为可执行调用的核心模型，集群层可以将多个提供者包装成统一调用入口，代理层负责让调用表现为业务接口；参见[代码架构说明](https://dubbo.apache.org/en/overview/mannual/java-sdk/reference-manual/architecture/code-architecture/)。

基于这张职责图，可以提出三个可证伪问题。注册中心短暂不可用时，已有地址缓存是否还能支持调用？某个提供者失败后，当前方法是否会重试，重试发生在哪一层？增加一个扩展实现后，扩展发现、配置选择与调用执行分别在哪个阶段发生？这些答案依赖注册模式、协议、版本和配置，应从运行证据得出，不能只靠记忆某个默认值。

为读懂重试，给一次用户请求、每次实际远程尝试分别分配标识，并在提供者记录收到次数。模拟“服务端已完成但响应丢失”，观察是否产生第二次执行。如果业务是扣减或发放，必须说明幂等由谁保证；RPC 框架的重试策略不等于业务天然恰好执行一次。基础材料可复用[Dubbo 面试与机制](../distributed-system/rpc/dubbo.md)以及[超时与重试](../high-availability/timeout-and-retry.md)。

## 从阅读迁移到自己的设计

最终交付一页材料：版本和环境、入口与关键边界、一个成功时序、两个失败时序、可运行实验的位置。不要堆积几十个无解释的类名。能把自动配置中的条件思想迁移到扩展点选择，把 Netty 的消息边界迁移到 RPC 协议，把 Dubbo 的调用分层迁移到自己的代理与治理模块，阅读才产生了可复用的知识。

完成本课的标准是：三类框架各有一个经过验证的问题；每条结论能指向当前版本的源码或实验；未执行的推断明确标记；能在更换一个条件后预测行为并复测。本文给出的是训练方法与预期，不声称已替你在本机执行这些框架实验。
