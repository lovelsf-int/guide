## 把面试准备变成可检验的能力

> 围绕准备方法、案例、练习和评分标准，组织 Java 后端面试复习。

准备 Java 后端面试，可以围绕三个交付物展开：一份能解释取舍的知识清单、一个有证据的项目案例、一组能暴露短板的自测记录。每天读了多少页只是投入，能在追问下解释清楚才是结果。本文按准备、技术、面经、自测、成长和工作六个方向组织，帮助你把分散文章接成一个闭环。

## 先做一次 45 分钟诊断

拿一张空白纸，分别回答“一个 HTTP 请求怎样进入业务方法”“一次数据库更新失败会发生什么”“两个线程同时修改数据怎样避免覆盖”。每题先讲两分钟，再补一个反例，最后画出请求或状态变化。卡住时先记录关键词，结束后再查资料，避免把刚看过的答案误认为自己的能力。

用同一把尺子评分：0 分是无法描述；1 分是能背定义；2 分是能解释机制并举例；3 分是能分析边界和失败；4 分是有可复现的实验或项目证据。满分不是“每题说得越长越好”，而是在有限时间里抓住约束。比如解释事务时，只说 ACID 得到的是定义分；能指出异步消息与数据库提交不是一个原子操作，才进入工程分析。

## 演练：怎样回答“线程池参数是怎么设置的”

设定一个**练习场景**：接口每秒接受 300 个任务，每个任务平均占用工作线程 80 毫秒，其中大部分时间在等下游。稳定负载下，平均同时占用线程的任务数约为 `300 × 0.08 = 24`。这只是按平均量得到的起点，不能据此宣布“24 个线程足够”。尾延迟、流量突增、数据库连接数、下游限流以及 CPU 时间都会改变结果。

下一步把假设变成约束：下游最多给本服务 40 个并发连接，那么盲目把线程提高到 200，只会把等待转移到连接池。若队列允许积压 150 个任务，在 300 个任务每秒的处理能力下，光排队就可能消耗约半秒预算；实际延迟还取决于任务分布和服务速率。于是应先给请求确定总超时，再分配排队、下游调用和响应处理的预算。

可以这样回答：

> 我先根据到达速率和平均占用时间估算并发量，再用下游容量限制线程上限，并给队列设置容量和排队超时。压测观察吞吐量、P95/P99、拒绝率、CPU 与连接池等待。过载时明确返回失败或进入可恢复任务队列，避免无界积压。最终参数来自同一数据集的对照实验，不能只引用一个经验公式。

随后准备三个追问。第一，使用 `CallerRunsPolicy` 会让提交任务的线程执行任务，因此必须检查提交方是不是请求线程或 I/O 线程。第二，Future 超时不等于下游副作用撤销，仍需要幂等键或结果查询。第三，虚拟线程降低线程的部分成本，却没有增加数据库连接和下游配额。完整机制见[线程池最佳实践](../java/concurrent/java-thread-pool-best-practices.md)与[虚拟线程](../java/concurrent/virtual-thread.md)。

练习时运行三档负载：低于目标、目标负载、短时超过目标。每档保存相同的指标，记录是否发生拒绝、积压是否回落。**验收要求**：能够解释每个参数保护哪个资源，且失败时没有把已拒绝的任务描述成成功。这里给出的数值都是计算示例，需要通过实际压测验证。

## 把项目经历写成可以追问的故事

一段项目描述至少包含“约束—选择—实现—验证”四部分。例如：上传文档后解析时间较长，用户会重复提交；你为任务定义状态，把重复请求映射到同一业务任务；通过唯一约束和条件更新防止重复处理；最终用并发提交、消费者重启和解析失败三个实验确认行为。这样的表述比“使用 Redis 提升系统性能”更容易核实。

不要把部署成功等同于生产经验，也不要把开源项目已有能力全部写成个人贡献。可以明确说“基于某开源项目完成某项改造”，附上自己修改的模块、发现的问题和验收记录。没有基线就不写提升百分比，没有真实流量就把结果标为本地实验。简历一页可以只保留两项最有把握的改动，细节放进[项目证据与简历指南](../interview-preparation/resume-guide.md)对应的材料中。

## 如何利用面经，避免被题量牵着走

将一份面经拆成“考点、追问、回答证据、下一步练习”四列，不需要照搬问题顺序。不同公司问到相似问题，可以合并到同一个知识节点。例如“缓存击穿”“热点数据失效”“一万个请求同时查空”可能都要求讨论同一条回源链路，但限制条件未必相同。

没有公开来源的面试对话不能写成某公司真实面经。练习材料应标注模拟；历史面经也只代表该次经历，不能推断今天的固定题库。本站的[面经与复盘入口](../interview-preparation/interview-experience.md)用于组织这类训练，答案回到机制文章核查。复盘时先找第一处推理断点，而不是把全部题重新抄一遍。

## 两周复习闭环与退出条件

第一至三天完成诊断和 Java、数据库基础补漏；第四至六天用自己的项目串联框架、缓存和消息；第七天做一次不看资料的模拟。第八至十天集中修复前三个短板；第十一至十二天练系统设计和源码追问；最后两天复查简历事实、练自我介绍与反问。时间不足时保留诊断、真实项目和复测三个环节，不要平均分配给所有技术名词。

每日练习控制为三个动作：复述昨天一个问题、完成今天一个最小实验、记录一个仍不确定的边界。成长和工作能力也用同样方式积累：技术方案留下取舍记录，故障留下时间线，代码评审说明修改理由。这样求职准备会成为平时工程工作的整理，而不是临时背诵。

进入下一轮投递前，至少满足以下条件：核心问题能先给 60 秒答案再接受追问；一个项目能画出成功与失败两条链路；所有简历数字都有来源；自测中原先的 0 分项已得到复测；遇到不会的问题能说明已知前提和验证路径。可继续使用[常见题自测](../interview-preparation/self-test-of-common-interview-questions.md)与[后端面试计划](../interview-preparation/backend-interview-plan.md)扩展练习。
